## How the request flows

`POST /api/v1/conversations/{id}/turns`:
1. **Endpoint:** sends `GetConversationQuery`, so an invisible conversation is `404` before any body checks.
2. **Endpoint:** `ConversationRequests.ReadTurnAsync` validates the contract shape. An invalid body gets `400`.
3. **Endpoint:** sends a `SubmitTurnCommand`.
4. **Handler:**
   - `Conversation.Reserve` claims the `client_turn_id`;
   - a different message gets `Error` Conflict (`409`), and a duplicate awaits the first run;
   - otherwise it runs the `orders` agent inside `TurnActivity`.
5. **During the run, the tool:**
   - sends `GetOrderStatusQuery`, whose handler checks the id format and ownership;
   - records the outcome in `TurnActivity`;
   - returns an `OrderStatusResult` to the model.
6. **Handler:** derives `ReplyKind` from the recorded outcomes and returns `Result<Turn>`.
7. **Endpoint:** `Match`. A success becomes `TurnResult.From(turn)` (contract JSON); a failure becomes `ApiResults.Problem`.

## Interview answers (assistant-drafted reference)

1. *Why keep endpoints thin, and where do authorization and idempotency belong?* An endpoint's job is translation: HTTP in, a use case, HTTP out. If business rules live there, every other entry point (an agent tool, DevUI, a future queue consumer) has to copy them or skip them. Here the ownership check sits in the query handler and the idempotency check in the command handler. The HTTP endpoint and the model's tool both go through the same handler, so neither can bypass the check.
2. *What do architecture tests protect that the compiler cannot when layers share one project?* With separate projects, a missing project reference stops Application using Infrastructure at compile time. In one project everything can see everything, so the boundary only exists if a test checks it. The architecture tests read the compiled types' dependencies and fail on a forbidden one. The self-tests prove each rule can fail, so a rule that silently matches nothing can't pass unnoticed.

## Course versus current implementation

The course (`dn-program`) composes everything in one `Program.cs`, which is fine for a teaching sample. This lab now uses modules and layers, as in the owner's SabiTutor platform, scaled down to folders: see the "not adopted" table in the ADR. References:
- Microsoft's Clean Architecture guide (`ms-clean-architecture`);
- its CQRS handler guidance (`ms-cqrs`);
- the ArchUnitNET docs (`archunitnet-docs`).

## Tradeoff I can defend

Folders plus architecture tests instead of projects. That means one project to build and no reference ceremony. The cost is that enforcement comes from a test, not the compiler, and the test has a small blind spot (bare `typeof`). For a four-module learning API that is the right side of the trade. If the API grew many modules or teams, separate projects would be worth their cost.
