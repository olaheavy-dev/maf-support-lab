# L37 - Add bound Python approvals for simulated mutations

> **Authorship:** The assistant (Claude Code) implemented this ticket and drafted this note. Per the owner's choice, interview questions and tips are given in chat rather than recorded here.

## What I built

Ported L10 to Python (MAF Python 1.25.0):
- **Native approval:** `write_tools.py` has three MAF tools with `approval_mode="always_require"`: `cancel_order` (orders), `refund_order` (billing) and `create_ticket` (technical). MAF pauses with a `function_approval_request` instead of running them. None takes a customer id or a confirmation.
- **Bound operations** (`operations.py`):
  - an `Operation` is bound, when created, to the customer, conversation, kind and exact arguments (canonical JSON), with a 15-minute expiry from `policies.json`;
  - the decision is recorded once;
  - execution happens only inside `approval_scope(operation)`, for the same customer, the same kind and exactly the same arguments, and at most once.
- **Business authorization, separate from consent** (`WriteHandlers`, `policy.py`):
  - ownership and eligibility (cancel: processing only; refund: delivered, within 30 days of the reference time, not refunded before) are checked **before asking** and **again at execution**;
  - the writes change `SimulatedState` (orders, refund payments `RFD-…`/`PAY-8001+`, tickets `TKT-…`), never the fixture files.
- **The gate** (`approval_gate.py`):
  - one valid, eligible request becomes an operation; the turn ends `awaiting_approval` with `pending_approval`;
  - anything else is declined natively (`to_function_approval_response(approved=False)`, so the tool never runs), and the reply states the factual reason, written by code (`not_eligible`, `not_found`);
  - bounded at 3 rounds; DevUI chats (no conversation) are declined.
- **API** (`api.py`):
  - `POST /api/v1/conversations/{id}/approvals/{approval_id}` with the binding checks (404, `409 approval_mismatch`, `409 approval_already_decided`, `410 approval_expired`) and a reservation per approval, so a repeat replays and a different decision conflicts;
  - the resume answers the native request in the conversation's own session;
  - follow-up requests are declined;
  - a failed resume still completes a factual, replayable turn;
  - `GET /api/v1/operations/{id}` (owner only);
  - turns carry `pending_approval`, `operations` and `resumed_from_turn_id`; conversations list `pending_approvals`.
- **Workflow:** L18's `write-not-available` executor is removed; write requests go to their specialist. The fake model requests writes like .NET's.

## A real bug found live, and how it's now caught in fake mode

- **Found:** the first live run committed the cancellation (correct and safe), but the **follow-up model call failed** with Anthropic `400: unexpected tool_use_id found in tool_result blocks`, and the customer got the factual fallback text.
  - **Cause 1:** stored history keeps only plain text (L19), and **MAF Python does not re-add the paused tool call** before the native answer's result. (I briefly concluded it did. A trace of the decline path proved otherwise, and my earlier "not caught" mutation turned out to be a script whose replacement hadn't changed the code.)
  - **Cause 2:** my explanatory note was placed **between** the call and its result.
- **Fix:**
  - `approval_gate.answer()` re-sends the paused call right before the decision;
  - declines carry no note, and the reply states the reason from code;
  - the decision's `reason` is recorded on the operation for audit. MAF Python's approval response has no reason field, unlike .NET's `CreateResponse(approved, reason)`. That's an SDK convention difference with no observable change, because the rejection reply is factual in both.
- **So it can't recur:**
  - the fake model now **enforces Anthropic's pairing rule** (`check_tool_pairing`), so fake-mode tests fail on it;
  - the approve test requires the model's own reply ("Done: …"), not the fallback ("Done. …");
  - the live test asserts the same.
- **Mutations:** not re-sending the call → 10 failing; putting a note between call and result → 10 failing.

## Course versus current implementation

| Course | Here | Why |
| --- | --- | --- |
| `tools.py` approval with a caller-supplied confirmation | Native `always_require` tools; only the customer's bound decision answers them | A flag the caller or model sets isn't consent |
| Tools invent results; no eligibility | Module checks before and at execution; factual results | Consent isn't authorization |
| No operation record | `Operation` with status, result, failure, expiry; `GET /operations/{id}` | Authoritative state independent of any connection |

## Tradeoff I can defend

**Factual decline replies from code, not from the model.** .NET passes the decline reason to the model and lets it explain. In Python, a note can't sit next to the tool result (Anthropic 400), so the reply states the reason directly. It's less natural-sounding, but always correct, needs one model call fewer, and can't be talked out of the facts.
