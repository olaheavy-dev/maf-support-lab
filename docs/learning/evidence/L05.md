# L05 - Build the first .NET order-status agent and DevUI

> **Authorship:** The assistant (Claude Code) implemented this ticket and drafted this note. The interview answers are **assistant-drafted reference answers**.

## What I built

- **Fixtures and ownership:** `FixtureCatalog` loads `fixtures/data/orders.json`, copied into the build output. `OrderService.FindForCurrentCustomer` returns an order only for its owner, taking the principal from `IPrincipalSource`.
- **Tool:** `get_order_status(orderId)`.
  - The only model-controlled input is the order id. The `ORD-NNNN` format is checked.
  - Results are `found`, `not_found`, or `invalid_order_id`, with no other customer's data ever included.
  - The tool records its outcome for the turn (`TurnActivity`, scoped to the turn's async flow).
- **Agent:** `OrdersAgentFactory` builds one `ChatClientAgent` (MAF 1.28.0) named `orders`, with instructions and the single tool. `SupportAgents` holds the instance shared by the API and DevUI.
- **Model boundary:** `FakeChatClient` is the default in Fake mode and is scriptable in tests. Live mode still uses the Claude client from L03.
- **Contract API:**
  - create and get conversation, submit and get turn;
  - JSON responses, with unknown fields rejected;
  - `client_turn_id` replay and conflict;
  - non-owners get `404`;
  - `reply.kind` derived from tool facts;
  - problems in RFC 9457 format with our contract codes.
- **DevUI (Development only):** `AddAIAgent("orders", …)` returns the shared instance, plus OpenAI Responses/Conversations and `AddDevUI`/`MapDevUI`.
- **Tests:** 20 new, 32 total plus 1 explicit live test. Every API body is validated against the shared `contracts/schemas` using JsonSchema.Net 9.6.0.

## How the request flows

1. `POST …/turns`: the body is validated, and the conversation is looked up for the current principal.
2. `TurnActivity.Begin()` starts the turn record.
3. `orders.RunAsync(message)`: MAF's function-invocation loop calls the model.
4. The model asks for `get_order_status`; MAF runs the tool, which asks `OrderService` and records the outcome.
5. The tool result goes back to the model, which writes the reply.
6. The API builds the `TurnResult`. `reply.kind` comes from the recorded outcome. The result is stored for `client_turn_id` replay and returned.

## Findings

1. **DevUI's loopback guard covers our routes in Development.** `DevUIAccessControlMiddleware` protects any path *containing* the segments `/v1/responses` or `/v1/conversations`, so `/api/v1/conversations` is loopback-only in Development. Its 403 uses ASP.NET's own problem format, not our contract codes. The test host now presents a loopback caller. This matters for the L23 frontend proxy (Host header) and is documented in `src/dotnet/README.md`.
2. **`ChatClientAgent` runs the tool loop by itself.** The fake client returns a `FunctionCallContent`; the agent invoked the tool and called the model again with the result, with no extra wrapping. This was confirmed by the two-call count in the misbehaving-model test.
3. **Tool parameter naming:** `AIFunctionFactory` uses the C# parameter name (`orderId`) in the tool schema. The scripted fake model must use the same name.

## Codex review (PR #69)

Codex found two valid P2 bugs, each reproduced with a failing test before fixing:

1. **Explicit `null` fields caused a 500.** `[JsonRequired]` only requires a property to be present, so `"message": null` deserialized and then crashed. Fix: null checks before validating contents. Tests: `Null_fields_are_a_contract_problem_not_a_server_error` (both fields).
2. **Concurrent duplicates ran the agent twice.** Two requests with the same `client_turn_id` both passed the "seen before?" check while the first was still running. The model was called 4 times instead of 2, and a different message got `200` instead of `409`. Fix: `StoredConversation.Reserve` atomically claims the id with its message *before* running. The owner runs the turn; same-message duplicates await that run; different messages get `409` immediately. A failed run releases the reservation so the client can retry. Tests: `Concurrent_duplicates_run_the_agent_once_and_share_the_result` and `Concurrent_reuse_with_a_different_message_is_a_conflict`, which passed 5 consecutive runs.

After the fixes: 36 passed, 1 explicit live test not run.

## Interview answers (assistant-drafted reference)

1. *When should a model call a tool rather than answer from its prompt?* When the answer depends on facts the model doesn't have or mustn't guess, such as live or private data (an order's status) or an action. The prompt holds behavior; tools hold facts and actions. The tool is also where rules are enforced, because code runs it, not the model.
2. *How does DevUI relate to your application API?* DevUI is a developer tool that talks to the same agent through OpenAI-compatible endpoints. It's useful for chatting and seeing tool calls. Our API is the product contract. Both reach the same agent instance and the same tool, so the same ownership checks apply. DevUI is mapped only in Development and is never a production entry point.

## Tradeoff I can defend

`reply.kind` is derived from what the tool recorded, not from structured model output. It's deterministic and impossible for the model to fake, and it's enough for a single read-only tool. The cost is that richer kinds (`escalation_offer`, `refusal`) need more recorded facts. Triage and structured routing replace this in L07/L08.
