# L19 - Implement isolated Python conversation sessions

> **Authorship:** The assistant (Claude Code) implemented this ticket and drafted this note. Per the owner's choice, interview questions and tips are given in chat rather than recorded here.

## What I built

Ported L09 to Python (MAF Python 1.25.0):
- **Native sessions per conversation** (`sessions.py`, `ConversationSessions`):
  - each conversation owns one MAF `AgentSession` per specialist, created with `agent.create_session()` on first use and passed to `agent.run(..., session=...)`;
  - the agents stay shared, reusable definitions;
  - nothing is global: the sessions live on the `Conversation`, which is reached only through `find_owned`.
- **Bounded history** (`BoundedHistory`, a subclass of MAF's `InMemoryHistoryProvider`, on each specialist):
  - stores only plain user and assistant messages, trimmed to 12;
  - drops tool calls and results (no orphans when trimming) and context notes;
  - MAF stores them in `session.state["in_memory"]["messages"]`, under the provider's source id. My first diagnostic read the wrong key, and a test caught it.
- **Verified context** (`ConversationContext`):
  - the last route, and an order id **only when a tool found it for this customer** (`TurnActivity` → `SupportReply.verified_order_id`);
  - updated only after completed turns;
  - a follow-up without an id uses it (`TriageOutcome.effective_order_id`), so there's no "which order?";
  - the specialist gets a one-turn note (a `system` message authored `support-context`, right after the customer's message); triage gets the previous route as a hint.
- **The fake model** reads the context note like a real model would.
- **Concurrency policy** (unchanged from L18, now tested for history): one turn at a time per conversation. A different turn → `409 turn_in_progress` (rejected, not queued); a duplicate → waits for the one run; other conversations aren't affected.

## Course versus current implementation

| Course | Here | Why |
| --- | --- | --- |
| Specialists run statelessly on the triage summary | A native `AgentSession` per conversation per specialist, on the original message | Follow-ups need the conversation's own history |
| No history bound | 12 plain messages; tool traffic and notes dropped | Context limits and cost; no orphaned tool results |
| No concurrency rule | One turn at a time (`409 turn_in_progress`) | A session must not be written by two runs at once |
| Context from free text | Only tool-verified facts | A mentioned id isn't proof the customer owns it |

## Tradeoff I can defend

**Reject, don't queue, a concurrent turn.** Queueing hides latency, and could run a stale message after the first answer changed things. Rejecting with `409` is deterministic, keeps one writer per session, and lets the client decide. The cost: a client that fires two messages quickly must retry the second.
