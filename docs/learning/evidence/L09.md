# L09 - Add per-conversation sessions and preserve context

> **Authorship:** The assistant (Claude Code) implemented this ticket and drafted this note. Per the owner's choice, interview questions and tips are given in chat rather than recorded here.

## What I built

- **Agent lifetime vs conversation state.** The agents stay shared singletons. `ConversationSessions` (Triage/Infrastructure/Routing) gives each conversation its own MAF `AgentSession` per specialist, created on first use and reused on later turns. `SpecialistExecutor` runs the agent with that session.
- **Bounded history:**
  - `ConversationHistory.CreateProvider()` puts an `InMemoryChatHistoryProvider` on every specialist, with our `BoundedHistoryReducer` (12 plain messages; tool calls, tool results and context notes dropped).
  - It's our own reducer because M.E.AI's `MessageCountingChatReducer` is marked experimental (`MEAI001`) in 10.11.
- **Verified context:**
  - `Conversation` keeps a `ConversationContext`: the last route target, and a `VerifiedOrderId` set only when a tool recorded `Found` for an order. `TurnActivity.Record(outcome, orderId)` is used by `get_order_status` and `get_invoice`.
  - On a follow-up without an id, `TriageOutcome.EffectiveOrderId` uses the verified id (so no "which order?"), and the specialist gets a one-turn context note.
  - Triage stays stateless, with a previous-route hint.
- **One turn at a time:**
  - `Conversation.Reserve` is now atomic, under one lock, with three outcomes: Owner, Duplicate (same `client_turn_id`: wait or replay) and Busy (a different turn is running → `409 turn_in_progress`).
  - The turn id is assigned at reservation, so `GET /conversations/{id}` reports `active_turn_id` while the turn runs.
- **Plumbing:**
  - `ISupportRouter.RouteAsync(RoutingRequest)`: conversation id, message and context.
  - A `support.triage.order_id_from_context` span tag.
  - The fake model reads the context note like a real model would.

## How the request flows

1. The handler checks ownership, then `Reserve`: a different turn running → `409`; a duplicate → wait or replay.
2. `RouteAsync(new RoutingRequest(conversationId, message, conversation.Context))`.
3. **Triage** classifies the message, with a previous-route hint. If an order-specific action names no id but the context holds a verified one, it's used.
4. **The specialist:**
   - gets its session for this conversation (bounded history comes back);
   - its input is the customer's message, then the context note if needed;
   - it runs, and tools record outcomes and verified ids.
5. The reply carries `VerifiedOrderId`. `Conversation.Complete` stores the turn, updates the context, and clears `active_turn_id`.

  - a second conversation has no context, and another customer gets `404` on the first;
  - the specialist sees earlier turns, at most `MaxMessages`, and exactly one context note after two follow-ups;
  - each earlier user message reaches the specialist exactly once;
  - while one turn is held, `active_turn_id` is set, a different turn gets `409 turn_in_progress`, another conversation answers normally, and afterwards `active_turn_id` is null.
- **Mutation checks** (each reverted):
  - Remembering the *mentioned* order instead of the verified one: the unverified-order tests fail.
  - Running without the session: the native-session test fails.
  - Removing the Busy check: the one-turn-at-a-time test fails.
  - Removing the reducer: the bounded-history test fails.
  - A storage filter without MAF's history exclusion: the exactly-once test fails.
  - Storing *and* passing through context notes: the context-note test fails (expected 1, got 2).
  - **One mutation wasn't caught at first:** storing notes while the reducer still dropped them changed nothing visible. While investigating, the context-note test was found to be vacuous: its second follow-up was unroutable, so only one note was ever sent. It was strengthened.
- **Two real bugs, found and fixed during the ticket:**
  1. **Duplicated history.** Setting `StorageInputRequestMessageFilter` *replaces* MAF's default filter, which skips messages loaded from history, so every turn re-saved the whole history (turn 1 was stored four times by turn 3). Our filter now applies the same exclusion via `GetAgentRequestMessageSourceType()`, and the exactly-once test guards it. The 12-message cap had hidden this from the other tests.
  2. **Anthropic rejected the context note** with HTTP 400 (`role 'system' must follow a 'user' message …`), because the note came after the previous assistant reply. It now follows the customer's message. Found only by the live check; the fake model accepts any order.

## Course versus current implementation

| Course | Here | Why |
| --- | --- | --- |
| Specialists run statelessly on the triage summary each turn | Native `AgentSession` per conversation per specialist, original message | Follow-ups need the conversation's own history |
| No history bound | 12-message cap; tool traffic dropped | Context limits and cost; no orphaned tool results |
| No concurrency rule | One turn at a time per conversation, `409 turn_in_progress` (contract) | Sessions aren't safe to use from two runs at once; deterministic, documented behaviour |
| Context from free text | Only tool-verified facts become context | A mentioned id isn't proof the customer owns it |

## Tradeoff I can defend

**Reject, don't queue, a second turn.** Queuing would hide latency and could run a stale message after the first answer changed the situation. Rejecting with `409` is deterministic and lets the client decide. It also guarantees one run per session at a time, which keeps the session model simple. The cost: a client that sends two messages quickly must retry the second.
