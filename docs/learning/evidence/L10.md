# L10 - Require bound approval for simulated support mutations

> **Authorship:** The assistant (Claude Code) implemented this ticket and drafted this note. Per the owner's choice, interview questions and tips are given in chat rather than recorded here.

## What I built

- **Three write tools, all native-approval-gated:**
  - `cancel_order` (orders), `refund_order` (billing), `create_ticket` (technical), in `Operations/Presentation/OperationTools`;
  - each is a MAF/M.E.AI `ApprovalRequiredAIFunction`;
  - no tool takes a customer id or a "confirmed" flag.
- **`Operations` module:**
  - `Operation` binds an approval to the customer, conversation, kind and exact arguments. `OperationArguments` compares canonical JSON with sorted keys.
  - It records the decision once, runs the write at most once, and has a 15-minute expiry.
  - `OperationService.ProposeAsync` checks eligibility **before** asking. `ExecuteApprovedAsync` runs only the operation in the trusted `ApprovalScope`, with the same kind, the same arguments and the same customer.
  - `GET /api/v1/operations/{id}` returns the authoritative status.
- **Module-owned writes, over in-memory simulated state** (fixtures untouched):
  - `CancelOrderWriteHandler`: `processing` only.
  - `RefundOrderWriteHandler`: `delivered`, within 30 days of the fixtures' `reference_time`, not already refunded; full amount; `RFD-…` plus a refund payment.
  - `CreateTicketWriteHandler`: `TKT-…`; a related order must be the customer's own.
  - Rules come from `fixtures/data/policies.json` (`SupportPolicy`, `OrderRules`).
- **The adapter:**
  - `ApprovalGate` turns a native `ToolApprovalRequestContent` into a proposed operation (the turn ends `awaiting_approval` with `pending_approval`), or declines it natively with the factual reason (`not_eligible`, `not_found`, `clarification`; no operation).
  - `SupportWorkflowRouter.ResumeAsync` answers the native request in the conversation's session (`CreateResponse(approved, reason)`) and declines any follow-up request, bounded to 3.
  - `DecideApprovalCommandHandler` handles `POST …/approvals/{approval_id}`.
- **History:** native approval requests and responses are dropped from history, because approvals are operation state.
- **Contract:** turns carry `pending_approval`, `operations` and `resumed_from_turn_id`; conversations carry `pending_approvals`. The reply kinds `not_eligible`, `approval_request` and `approval_result` are now used. L08's `write-not-available` executor is removed.

## How the request flows

1. "Please cancel order ORD-1003." → triage → `orders-specialist`.
2. The model calls `cancel_order(orderId: "ORD-1003")`. MAF's function invocation **does not run it**; it returns a `ToolApprovalRequestContent`.
3. `ApprovalGate` maps it to `cancel_order {"order_id":"ORD-1003"}`. Orders checks that the order is this customer's and still `processing`. An `Operation` and approval are created and bound, and the native request is held. The turn ends `awaiting_approval`.
4. `POST …/approvals/appr_…` with `{operation_id, decision}` goes through the binding checks, then reserves the conversation turn (repeats replay) and records the decision once.
5. **Approve:** `ApprovalScope(operation)` → the native response "approved" → the framework runs the tool → `ExecuteApprovedAsync` checks kind, arguments and customer → Orders re-checks and cancels → `committed` with `{"order_id","order_status":"cancelled"}` → the model reports it.
   **Reject:** the native "rejected" response; the tool never runs → `rejected`, with a fixed reply.

## Codex review (PR #76)

Two valid P2 findings. Each was reproduced by a failing test before being fixed:
1. **A failed resumed run made a recorded decision un-replayable.**
   - The handler abandoned the turn reservation on an exception, while the operation kept the decision. A repeat then got `409 approval_already_decided` forever, and there was no turn to retrieve.
   - **Fix:** the turn always finishes with a factual reply built from the operation's recorded status (committed, rejected, failed). It's stored, so a repeat replays it, and the write is never re-run.
   - **Test:** `A_decision_stays_replayable_when_the_resumed_model_call_fails` (approve and reject), with a model that fails after the tool result.
2. **A refund summary could exceed the contract's 500-character limit**, when given a valid 500-character reason.
   - **Fix:** summaries are capped at 500 characters with "…". The full reason stays in `arguments`, which is what's approved and executed.
   - **Test:** `A_refund_with_the_longest_allowed_reason_still_has_a_contract_valid_summary`, which validates the turn and conversation against the schemas.

After the fixes: 164 passed, 5 explicit live tests not run.

## Contract check (native SDK vs contract 1.0)

- **Minimal native example** (fake model, MAF 1.28.0 / M.E.AI 10.11):
  - the tool isn't run before the decision, and the request carries the exact tool call;
  - approve → the tool runs once;
  - reject → the tool never runs, and the model is told it was "rejected by the approver and must not be retried" with the reason;
  - it works with our bounded history, because the response carries the tool call.
- **Result: no contract change.** Native `kind` and `arguments` come from the tool call, and the decision `reason` maps to the response reason. Binding, expiry and operation state are server responsibilities, as the contract already says. This is recorded in `contracts/README.md` (revision history: "1.0 (checked)").

## Course versus current implementation

| Course | Here | Why |
| --- | --- | --- |
| `RefundWorkflowRunner` answers the native request from a `customerConfirmed` bool passed by the caller | The turn ends `awaiting_approval`; only the customer's later decision, bound to the operation, answers it | A boolean the caller (or model) supplies isn't a customer decision |
| `ProcessRefund`/`CreateSupportTicket` invent results; no eligibility or ownership | Module write handlers enforce ownership and eligibility before and at execution | Business authorization is separate from approval |
| No operation record or expiry | `Operation` with status, result, failure and a 15-minute expiry; `GET /operations/{id}` | Authoritative state independent of any connection |

## Tradeoff I can defend

**The agent asks; code decides twice.** We check eligibility before asking (so customers aren't asked to approve impossible actions) *and* again at execution (state can change in between). That costs a duplicated check, but each check protects a different moment, and the test with two approvals for one order shows why both are needed.
