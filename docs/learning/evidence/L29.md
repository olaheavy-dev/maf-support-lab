# L29 - Set up post-build evaluation projects, datasets, and result contracts

> **Authorship:** The assistant (Claude Code) implemented this ticket and drafted this note. Per the owner's choice, interview questions and tips are given in chat rather than recorded here.

## What I built

- **Prerequisite confirmed:** both backends build and pass their feature and contract checks, and L21's cross-backend probes agree on all 29 probes.
- **Contracts** (`evaluations/schemas`, JSON Schema 2020-12, both versioned `1.0`):
  - **`evaluation-dataset`:** versioned cases with `split` (development or heldout), `reset` (a fresh conversation, or a fresh store for write cases), optional `context` (fixture records), steps (`send`, `resend_previous`, `decide`, `send_raw`, `as_principal`) and the expected observable facts, plus a `live_run` budget.
  - **`evaluation-run`:** run identity (run id, times, backend, source commit, model mode and id, dataset id, version and splits, scorer, runner, configuration); per-case status, latency, step evidence and checks; usage availability; and a summary.
- **Datasets** (`evaluations/datasets`, 27 cases): success 8, ambiguity 4, denial 6, failure 4, adversarial 5. They are generated from `fixtures/scenarios` (S01–S18) plus 9 evaluation-only cases by `evaluations/tools/build_datasets.py`. 7 cases are held out. The failure dataset (fake-model markers) is not live-eligible.
- **`evaluations/dotnet/Support.Evaluations`:** a console runner with no reference to any application project.
  - `validate` checks every dataset against its schema, plus unique case ids.
  - `run` sends each case through the public API, streamed, so tool calls are visible from `turn.progress`. It applies one named check per expected fact and writes a run document that it validates against the run schema first.
  - Write cases are skipped without `--allow-writes`, and a case needing a customer with no backend process is skipped with the reason.
- **`evaluations/dotnet/Support.Evaluations.Tests`** (25 tests): the committed datasets; malformed or unversioned datasets and runs rejected; and the runner over a fake backend (pass, failure naming the fact, leaked data, problem responses, write and customer skips, splits, a safe error, a decision answering the earlier approval).
- **`evaluations/python`:** its own locked uv project (`jsonschema` only) and the shell L31 builds on.
  - It applies the same contract checks, plus two rules a schema can't express: `context` references must name real fixture records, and a run's summary must add up.
  - CLI: `python -m support_evaluations validate [RESULTS_DIR]`. 23 tests.
- **`evaluations/tools/run_against_backends.py`:** the data-to-result flow against **both real backends** in fake mode, two processes each (`CUST-1001`, `CUST-1002`) on one store, started by L21's harness. It runs in CI's `cross-backend` job and uploads the `evaluation-results` artifact.
- **CI and dependencies:** a new required `evaluations` job; Dependabot `uv` for `evaluations/python`. `evaluations/results/` is ignored by Git.

## What the datasets found on the first run

1. **A real cross-backend difference, now fixed.** When the model asks for a write tool, Python's stream showed a `tool_call` progress event and .NET's didn't. In .NET the call arrives wrapped in a `ToolApprovalRequestContent`, which the stream forwarder ignored. L21's probes compared stages only for a read turn, so they missed it.
   - .NET now also reports the call inside an approval request. The model did call the tool; it just hasn't run.
   - New regression tests in **both** backends: the `cancel_order` tool call comes before the pause, and nothing changed.
2. **A wrong case of mine.** The follow-up "And what is its status now?" has no domain words, so both fake triages correctly leave it unrouted. It's now "Has that order shipped yet?", which exercises the verified-order context.
3. **Wrong fixture ids.** The payment context reference first said `PAY-5006`, but the fixtures use `PAY-7xxx` (the refund is `PAY-7101`). The Python contract check now rejects references to missing records.
   - The same wrong ids sat in L21's probe normalizer, in its list of fixture payment ids to keep. They never appeared in compared fields, so nothing was hidden, but the list is now correct, along with its test example.

## The stretch: a held-out ambiguous query

`support-ambiguity/vague-request` ("Can you help me with something?") is `heldout`. If prompts were tuned until this exact sentence routed "correctly", the case would only show that the prompt memorized it, not that the system handles unseen vague requests. A held-out case measures generalization only while nobody optimizes against it. The runner runs it only when `--split heldout` is asked for, and the run records which splits were run.

## Course versus current implementation

| Course | Here | Why |
| --- | --- | --- |
| Evaluation by watching traces in DevUI and Aspire | Versioned datasets, a result contract, and a runner that asserts observable facts | Repeatable, comparable across backends, and usable in CI |
| — | Evaluation code in its own projects | The support APIs never ship evaluator dependencies |

## Tradeoff I can defend

**Black-box over HTTP instead of in-process.** The runner talks to a backend through the public API, the same way a client does. It can't see internal tool arguments or session contents, only the stream's tool names and the stored results. That makes it backend-agnostic and immune to SDK serialization changes, and it's why it caught a real .NET/Python stream difference. Native evaluators (L30/L31), which do see internals, add that depth separately.
