# L31 - Integrate native Python local agent and workflow evaluations

> **Authorship:** The assistant (Claude Code) implemented this ticket and drafted this note. Per the owner's choice, interview questions and tips are given in chat rather than recorded here.

## What I built

- **`agent-framework-core==1.25.0`** in `evaluations/python`'s own manifest (locked), the same release as the backend. It's core only, because the evaluated agent is scripted. The backend's manifest is untouched.
- **`support_evaluations/native.py`**, the Python counterpart of L30:
  - **The fake support agent:** a MAF `Agent` over a scripted `BaseChatClient`, with MAF's real `FunctionInvocationLayer` and `ChatMiddlewareLayer`, counting every call.
    - Its tools have the Python backend's names and **snake_case** parameters over the shared fixtures, and reads check ownership.
    - The writes are `@tool(approval_mode="always_require")` and raise if ever run.
  - **The checks** through `LocalEvaluator`: MAF's `tool_call_args_match`, plus `writes_wait_for_approval`, `no_unexpected_writes`, `record_ids_are_grounded` and `cites_found_record`, written with `@evaluator`. They have the same semantics as .NET's.
  - **`record`:** `evaluate_agent(agent=…, queries=…, expected_tool_calls=…)`. Python's `EvalResults` doesn't return the evaluated conversations, so a `RecordingEvaluator` implements MAF's `Evaluator` protocol around `LocalEvaluator` and keeps them. It writes 11 captures to `evaluations/recordings/python/`, in the same capture schema as .NET.
  - **`evaluate`:** `evaluate_agent(responses=…, queries=…)`, which skips running the agent.
    - It **fails on any model call**, refuses stale captures and refuses missing or duplicated case recordings (the same rules Codex asked for in L30).
    - It writes run documents (`backend: python`, schema 1.2) with an evidence link to the file actually scored.
  - **`workflow`:** `evaluate_workflow` on a one-agent workflow (`WorkflowBuilder(start_executor=agent)`), scored overall and per agent (`sub_results`).
- **CI:** the `evaluations` job runs `native evaluate` and `native workflow`.
- **ADR 0004:** three Python rows (below). **ADR 0001:** the package row.

## SDK differences found (ADR 0004)

| Topic | .NET (L30) | Python (L31) |
| --- | --- | --- |
| A paused write in the response | `ToolApprovalRequestContent` **replaces** the call, so live `ToolCallArgsMatch` says "not called" | The `function_call` is **kept** and a `function_approval_request` added, so live `tool_call_args_match` sees it |
| Evaluated items | `AgentEvaluationResults.InputItems` | Not returned by `EvalResults`; kept by a protocol wrapper |
| API status | Stable in 1.28.0 | **Experimental** in 1.25.0 (`ExperimentalWarning: [EVALS]`; filtered in pytest, recorded here) |
| Orchestration | `agent.EvaluateAsync(...)` overloads | `evaluate_agent(...)` and `evaluate_workflow(...)` with keyword arguments; workflows per agent |
| Argument names | C# (`orderId`), mapped from canonical names | snake_case: the canonical names as is |

The two SDKs' captures of the same case (`order-status`) differ only in argument naming and in the tool result's JSON spacing. The evidence is otherwise identical.

## Tradeoff I can defend

**Wrapping `LocalEvaluator` to keep the items** instead of calling `agent.run` myself to get conversations. Running the agent separately and then evaluating would score a different run from the one recorded. The protocol wrapper records exactly the items MAF built and scored, which is the point of a capture. The cost is relying on the `Evaluator` protocol in an experimental API. It is small, and tested.

## Remaining questions

- If MAF .NET adopts Python's behaviour (keeping the call next to the approval request), the .NET normalization can go.
- The evaluation API is experimental in Python 1.25.0. A later release may rename it; the tests pin what is used.
