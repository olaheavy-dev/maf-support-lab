# L32 - Add budgeted model-based quality evaluation for both backends

> **Authorship:** The assistant (Claude Code) implemented this ticket and drafted this note. Per the owner's choice, interview questions and tips are given in chat rather than recorded here.

## What I built

The owner's decisions (2026-11-12) were: judge `claude-haiku-5-5`; judge **live backend replies**; and a live-lane cap of **60 model calls, 1 repetition**. On that basis:

- **Packages** (evaluation project only): `Microsoft.Extensions.AI.Evaluation.Quality` **10.11.0**, which matches MAF 1.28's Microsoft.Extensions.AI 10.11. Version 11.0.0 would move that family ahead of MAF. The judge client uses `Anthropic` 13.7.0, the central version.
- **`evaluations/config/quality.json`:** everything that affects a score, pinned.
  - The judge and its max output.
  - The backends' live model and **per-turn cap of 4**.
  - Metrics: relevance and groundedness.
  - 4 read-only cases covering both customers, an answer and a denial: `order-status`, `invoice`, `knowledge-base` and `refund-outside-window`.
  - The budget: 60 calls, 1 repetition, concurrency 2.
  - 4 calibration answers.
- **`Support.Evaluations/Quality/`:**
  - `QualityConfig`: loads and checks the config, and computes the worst case (53).
  - `GroundingContext`: turns context references into the exact fixture records, plus the fixture clock for policies. An unknown reference is an error.
  - `CallBudget`: worst-case reservation, admitted in plan order. `BudgetedJudgeClient`: refuses any judge call without a reserved permit, and sums token usage and peak concurrency.
  - `QualityScorer`: runs the real `RelevanceEvaluator` and `GroundednessEvaluator`. A metric is `scored` only with a value and no error diagnostic.
  - `QualityLane`: plans and admits the samples, runs at most 2 at a time, stops new work on cancellation, checks calibration, and builds the result.
  - `QualityCommand`: `quality --live`. It refuses without `--live`, refuses a config whose worst case is over budget, and refuses when no key is set.
  - `LiveReplySource`: launches both backends in live mode.
- **`ProcessSession`:** an optional `LiveModel` for each backend's mode, model, key and per-turn cap. The key goes only into the child process environment, and `LiveModel.ToString()` omits it.
- **`evaluations/schemas/evaluation-quality.schema.json` (1.0):** the result validates itself before it is written. This is a separate schema rather than run-schema 1.3, because samples have a different shape from contract-check cases.
- **Docs:** `docs/evaluations/quality.md` (method, results, limitations, and the Foundry Safety follow-up), `evaluations/README.md`, `docs/testing.md`, and ADR 0001's package row.

## How the request flows

1. **Plan:** backend × case × repetition, then the calibration answers.
2. **Admit, in order:** a backend sample reserves 4 (its turn cap) + 2 (metrics) calls; a calibration answer reserves its metrics. Whatever doesn't fit is `skipped: budget`.
3. **Run, two at a time:** a new conversation and one question to a live backend, then one judge call per metric. Each judge call uses a permit granted from its reservation.
4. **Record:** answers, context, scores, the judge's reasons, statuses, the budget, judge usage, package versions, and the uncertainty statement. Calibration checks require each "high" answer to score above each "low" one.

## Verification (assistant-run, 2026-11-12)

- **Fake-judge tests** (`QualityTests`, 14, in CI). No model is called; the fake judge answers in the evaluators' `<S0>/<S1>/<S2>` format and goes through the real evaluators. They cover:
  - **The committed lane:** 12 samples scored, 21 judge calls, usage recorded, calibration passes.
  - **The config:** its worst case (53) fits within 60, and every case is read-only with resolvable context.
  - **A small budget (13):** the first 2 samples run and the rest are `skipped: budget`, with calls never over the budget.
  - **A judge exception:** recorded as an error with no score, and the exception text doesn't leak.
  - **Malformed judge output:** an error.
  - **Missing or unknown context:** groundedness is an error while relevance is still scored. The real evaluator doesn't call the judge at all without context.
  - **A failed backend turn:** an error, and not judged.
  - **Concurrency:** never more than 2 at once, for replies and for judge calls.
  - **Cancellation:** stops new work.
  - **An uncovered judge call:** refused.
  - **Calibration:** a pair the judge can't separate fails, and an unscored pair is inconclusive.
  - **Metric interpretation:** an error diagnostic or a missing value is never a score.
  - **The command:** refuses to run without `--live` or over budget.
- **Mutation checks (7/7 caught, each reverted):**

  | Mutation | Caught by |
  | --- | --- |
  | Admit every sample regardless of budget | the small-budget test |
  | A missing value counts as scored | the metric-interpretation test |
  | Error diagnostics ignored | the metric-interpretation test |
  | No concurrency gate | the concurrency test |
  | Cancellation ignored before a sample | the cancellation test |
  | Judge permit not enforced | the uncovered-call test |
  | A failed turn is still judged | the failed-turn test |

  The metric-interpretation test was added after the first round, because two mutations survived: the real evaluator always pairs a missing value with an error diagnostic, so nothing exercised the two separately. A first try at the permit mutation used `if (false)`, which doesn't compile under warnings-as-errors, so it was redone.
- **Full suite:** .NET **319 passed** (10 live skipped); Python evaluations 45 passed, with ruff and pyright clean; repository validation passes.
- **Live (authorized by the owner's decisions; billed):**
  - Command: `quality --live --source-commit 3e61ec3` on the L32 working tree.
  - Backends and judge both on `claude-haiku-5-5`.
  - **12/12 samples scored**, 0 errors. **53 of 60 calls reserved**, 21 of them judge calls.
  - Judge usage: **39,021 input and 6,555 output tokens**. The run took 44 s.
  - Means: .NET relevance 3.75, groundedness 4.25; Python relevance 4.0, groundedness 4.25.
  - Calibration all passed: relevance good 4 vs off-topic 1; groundedness good 5 vs contradicting 3; groundedness good 5 vs changed context 3.
  - Per-case scores and reasons are in `docs/evaluations/quality.md`.

## What the live run showed

- **The judge discriminates but compresses the scale.** For the changed-context answer, its reason said "fabricated… ungrounded and incorrect", yet the score was 3, not 1. Treat scores as relative to calibration, not as thresholds.
- **Groundedness can't check process claims.** The .NET refund-denial reply said "the approver declined the request". The fixture context can't confirm or refute that, so it still got 4. Whether an approval happened is answered by the operation record in the deterministic lane.
- **The backends are within one point on every case.** With a single sample, that difference is noise, not a ranking.

## Course versus current implementation

| Course | Here | Why |
| --- | --- | --- |
| Reading traces and outputs by hand (chapter 6) | AI judge with pinned settings, fixture context, calibration and a budget | Repeatable and comparable, and the cost is bounded |
| — | One budget for backend and judge calls, admitted in order | Cost is the main risk of a live lane, and deterministic admission makes skips reproducible |

## Tradeoff I can defend

**Reserving a backend turn's worst case (4 calls) instead of counting its real calls.** The support contract doesn't report model calls per turn. Adding that only for evaluation would change the API for a measurement tool. Reserving the cap makes the budget conservative (the real spend is at most what was reserved) at the cost of admitting fewer samples. With 60 calls this still fits the whole planned lane.
