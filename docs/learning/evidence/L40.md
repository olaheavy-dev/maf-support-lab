# L40 - Export Python traces, logs, and metrics to Aspire over OTLP

> **Authorship:** The assistant (Claude Code) implemented this ticket and drafted this note. Per the owner's choice, interview questions and tips are given in chat rather than recorded here.

## What I built

The Python backend's own telemetry (MAF Python 1.25.0, OpenTelemetry SDK 1.45.2, FastAPI 0.162.3, Aspire 13.6.4).

**Owner's decisions:**
- OTLP over **gRPC**;
- **our own `telemetry.py`**;
- for HTTP spans, **FastAPI's built-in telemetry**. I first offered the contrib instrumentation. My probe then showed FastAPI 0.162 already emits HTTP spans and metrics, so I asked again; installing both would have duplicated them.

**What's built:**
- **`support_agent/telemetry.py`**, run once per process:
  - one tracer, meter and logger provider, with gRPC OTLP exporters that read the AppHost's `OTEL_*` endpoint, headers (the dashboard key), certificate and interval;
  - the service identity: `support-api-python` or `support-devui-python`, the package version, the environment;
  - our own `TraceLogHandler` on the root logger. The SDK's `LoggingHandler` is deprecated in 1.45, and its replacement is a prerelease;
  - MAF's GenAI instrumentation, with message capture set **explicitly**;
  - bounded flush and shutdown.
- **Configuration:**
  - with no endpoint, nothing is exported;
  - a non-gRPC protocol with an endpoint set **fails at startup**;
  - `TELEMETRY__CAPTURE_SENSITIVE_DATA` (default false) is the only way to capture content.
- **Correlation:**
  - FastAPI's HTTP span, then our `support.turn` span (ids, outcome, agent, reply kind; error status and `error.type` on failure), then MAF's workflow, executor, `invoke_agent`, `chat` and `execute_tool` spans: **one trace per turn**. The detached turn task inherits the request's context.
  - The contract's `trace_id`, in turn results and problems, is that trace's id.
  - "Turn finished" and "Turn failed" log records carry ids and outcome, never message text.
- **Metrics**, with the same names and labels as .NET: `support.turns`, `support.turn.duration`, `support.tool.calls`, `support.operations`, `support.triage.decisions`. New: `support.stream.first_delta`, L20's time to the first streamed text.
- **AppHost:** `WithOtlpExporter(OtlpProtocol.Grpc)` on both Python resources.
- **The fake model** reports 100/20 tokens per call and its model name on streamed updates, with a switch to report no usage.

## What the SDKs actually do (probed, then tested)

1. **FastAPI 0.162 has built-in OpenTelemetry** (`fastapi/telemetry`). It uses our global providers, takes an `exclude` hook (we exclude `/health` and `/alive`), and never shuts down providers it didn't create. The contrib package would duplicate it.
2. **MAF Python records token usage once, per model call.** It doesn't repeat it at the agent layer, unlike MAF .NET (L06 needed a View), so a test pins 3 calls to exactly 3 × 100 input tokens.
3. **DevUI's executor calls MAF's `configure_otel_providers()` at start-up.** That adds exporters from the environment, and its fallback provider hard-codes `service.name = "agent-framework-server"`. Also, `serve(instrumentation_enabled=True)` turns on **sensitive capture unconditionally**.
   - `telemetry.py` installs our providers first and sets MAF's private "setup done" flag, so DevUI's call does nothing. DevUI's switch stays off.
   - A test makes a DevUI request and checks the providers, span processors and log handlers are unchanged. The test also fails if MAF renames the flag.
4. **A turn task inherits the request's trace context** (asyncio copies context variables when a task is created), so one turn is one trace even though it outlives its request.

## Bugs found

- **Exit hung for over a minute with an unreachable collector.** The gRPC exporters retry, and the SDK providers' own exit hooks have no time limit.
  - Fix: `shutdown_on_exit=False` on all three providers, and our own exit hook flushes and closes them within 5 s, in a daemon thread. The host's lifespan flush is limited to 2 s and runs off the event loop.
  - Measured: about 5.3 s to exit against a dead endpoint.
  - The per-provider mutation shows the **meter provider's** own hook is the one that held the process. The trace and log hooks finish quickly on their own, so all three are off and one bounded shutdown owns them.
- **A deprecation warning:** the SDK's `LoggingHandler` is deprecated in 1.45. It's replaced by our ~40-line handler on the stable logs API, rather than adding the prerelease contrib package.

## Course versus current implementation

| Course | Here | Why |
| --- | --- | --- |
| `configure_otel_providers()` / console exporters in a demo script | Python-owned providers, gRPC OTLP from the AppHost, one setup per process | Aspire launching Python doesn't instrument it; someone must own the providers |
| Sensitive data opt-in through an environment variable | An explicit setting, applied explicitly; the framework variable can't override it | A stray variable shouldn't put customer messages into telemetry |

## Tradeoff I can defend

**Setting MAF's private "setup done" flag instead of letting DevUI configure telemetry.** The public alternative is to let DevUI call `configure_otel_providers()` and own its providers. But that path hard-codes the service name and attaches its own exporters and handlers, so the DevUI process would report as `agent-framework-server` or duplicate telemetry. The flag is one line plus a test that fails if MAF changes it. The cost is depending on one private attribute, and the test makes that dependency visible.
