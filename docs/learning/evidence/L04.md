## What I built

- **Locked restore:** `RestorePackagesWithLockFile` for all .NET projects, plus `RestoreLockedMode` when `ContinuousIntegrationBuild=true`. Lock files are committed for Support.Api, Support.ServiceDefaults, and Support.Api.Tests. The SDK selection (10.0.403) was already recorded in `global.json` in L03.
- **AppHost exception:** no lock file, because Aspire picks OS-specific dashboard and orchestrator packages (the trial lock pinned `Aspire.Dashboard.Sdk.osx-arm64` and `Aspire.Hosting.Orchestration.osx-arm64`). It is pinned by the Aspire SDK version and central versions instead.
- **CI** (`repository-checks.yml`) now has three jobs:
  - `planning-and-contracts`: the earlier steps.
  - `dotnet`: SDK from `global.json`, NuGet cache keyed on the lock files, locked restore, Release build with warnings as errors, and tests in fake mode.
  - `repository-checks`: the required aggregate. It runs `if: always()` and passes only when every needed job's result is `success`.
- **Advisories separated:** NU1901–NU1904 are no longer errors in required builds. A new `dependency-audit.yml` fails on vulnerable direct or transitive NuGet packages (weekly, on demand, and on PRs that change versions).
- **Dependabot:** NuGet updates for `/Directory.Packages.props`, in groups: aspire, opentelemetry, agents-and-ai, microsoft-extensions, tests.
- **Docs:** `docs/testing.md` (offline vs live, local commands, lock-file workflow, advisories), `docs/repository-settings.md`, and `src/dotnet/README.md`.

## Verification

- **Locked restore, Release build, and tests** run locally with CI's environment variables: restore OK, build with 0 warnings and 0 errors, 12/12 tests pass.
- **Drift is caught:** changing `Anthropic` from 13.7.0 to 13.6.0 in `Directory.Packages.props` without updating the lock made the CI-style restore fail with `error NU1004: The package reference Anthropic version has changed from [13.7.0, ) to [13.6.0, )`. Reverted.
- **Finding:** hand-editing only a lock file's `resolved` value did *not* fail locked restore. Locked mode compares what the projects request with the lock file; package integrity is protected separately by the recorded content hashes. The realistic risk (a version changed without regenerating the lock) is what gets caught.
- **Aggregate gate:** the job's script was run locally with each outcome. success+success → pass; any `failure`, `skipped`, or `cancelled` → fail.
- **Vulnerability scan today:** `dotnet list package --vulnerable --include-transitive` reports no vulnerable packages in all four projects.
- All three YAML files parse.
- **Live CI proof (pending):** a deliberate failure on a throwaway draft PR, showing `repository-checks` go red, runs after the owner approves the commit.

## Interview answers (assistant-drafted reference)

1. *What makes a build reproducible?* The same inputs give the same outputs: a pinned SDK (`global.json`), pinned direct versions (central package versions), pinned transitive versions with content hashes (lock files), and a build that refuses to proceed when those disagree (locked mode in CI). Anything network-dependent and changing, such as vulnerability feeds, is kept out of the pass/fail decision.
2. *Why is one aggregate required check better than requiring each job?* Rulesets require check names. If a job is skipped or renamed, a directly required check can stay "pending" forever or vanish silently. One job that always runs and fails unless every job succeeded gives a single stable name to require. New language jobs are added to its `needs` without touching the ruleset.

## Tradeoff I can defend

**No lock file for the AppHost.** Locking it would force a lock regeneration whenever someone switches between macOS and Linux, and CI could never use locked mode for it. The AppHost is local development orchestration, not shipped code, and its versions are still pinned by the exact Aspire SDK version. The application projects that matter for behavior are fully locked.
