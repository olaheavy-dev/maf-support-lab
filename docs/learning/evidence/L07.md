# L07 - Implement validated triage and deterministic routing

> **Authorship:** The assistant (Claude Code) implemented this ticket and drafted this note. Per the owner's choice (2026-11-10), interview questions and tips are given in chat rather than recorded here.

## What I built

- **New `Triage` module** (L43 layout):
  - **Domain:** `TriageDecision`, `RouteTarget`, `RequestedAction`, `TurnRoute` (routed target or unrouted reason), `SupportReply` and `ReplyKind` (moved here from Conversations), and `RoutingRules`. The rules hold the deterministic decisions: which action belongs to which team, and which actions need an order id.
  - **Application:**
    - `TriageDecisionParser`, which validates model output against the full contract schema;
    - `TriageOutcome`, the contract's routed-request (original message plus validated fields) together with the route;
    - `ISupportRouter`;
    - `TriageMetrics`.
  - **Infrastructure:**
    - `TriageAgentFactory`: a JSON-only classifier with no tools, using a simplified model-facing schema;
    - `Routing/SupportWorkflowRouter`, which builds the MAF workflow per turn;
    - five executors: `triage`, `orders-specialist`, `ask-for-order-id`, `billing-placeholder`/`technical-placeholder`, and `unrouted`.
- **Workflow** (`Microsoft.Agents.AI.Workflows` 1.28.0, stable): `AddSwitch` with four cases and a **default**, so nothing can match no route. Executors declare their outputs with `[YieldsOutput(typeof(SupportReply))]`.
- **Conversations:** a turn stores a `TurnRoute`, and the API returns `route.status = routed | unrouted` with `target` or `unrouted_reason`. `SubmitTurnCommandHandler` calls `ISupportRouter` instead of the orders agent.
- **Placeholders:** billing and technical are routed, and answer `escalation_offer`: "…help isn't available in this version yet". This is the owner's choice. No specialist model is called, so nothing pretends to be operational.
- **Telemetry:**
  - a `Support.Workflows` source;
  - `support.triage.*` tags on the triage executor span (outcome, target, reason, action, order-id presence, model confidence);
  - a `support.triage.decisions` metric with bounded labels;
  - routing logs (a warning when unrouted, naming the rule, never the model's text).
- **Fake model:** keyword triage that returns contract JSON, plus the `[fake:triage-malformed]` and `[fake:triage-unknown-route]` markers. Triage calls are recognised by their JSON response format, so scripted tests keep controlling the specialist model.

## How the request flows

1. The handler checks idempotency as before. Then `ISupportRouter.RouteAsync(message)` builds the workflow and runs it in process.
2. **`triage` executor:** the triage agent returns JSON, and `TriageDecisionParser` validates it.
   - Invalid → `unrouted / invalid_model_output`.
   - `RoutingRules.Route`: an action that doesn't belong to the target, or `other` → `unrouted / ambiguous_request`.
   - The result is recorded on the span, in the metric, and in a log.
3. **The switch runs the first case that matches:**
   - orders with an order-specific action and no id → `ask-for-order-id`;
   - orders → `orders-specialist`, where the L05 agent receives the *original* message, and its tool reads the principal from DI;
   - billing or technical → placeholder;
   - default → `unrouted`.
4. The selected executor yields one `SupportReply` (route, reply kind decided in code, text). The handler stores the turn and returns the contract JSON.

## Course versus current implementation

| Course (Chapter 7) | Here | Why |
| --- | --- | --- |
| `TriageDecision` with `targetAgent`, `confidence`, summary, sentiment | Contract `triage-decision`: plus `requested_action` and `order_id`, snake_case | Shared contract with Python; action enables the consistency check |
| Parser `JsonSerializer.Deserialize`, throws on bad JSON | Full-schema validation → `invalid_model_output` fallback | Malformed output must not become a 500 or a guessed route |
| Three conditional edges; an unknown target matches none and the run silently ends | `AddSwitch` with a **default** executor | Every outcome has a defined reply |
| Triage agent has a customer tool | Triage has no tools and no customer data | A classifier doesn't need data; less to leak or inject |
| `EnableSensitiveData = true` on workflow telemetry | Not set: a no-op in 1.28.0 (release notes), and capture stays off | Release disagreement recorded |
| Spans `workflow_invoke` / `workflow.name` | `invoke_workflow {name}` / `gen_ai.workflow.name` | MAF 1.28.0 breaking change |
| Workflow registered once in DI | Built per turn | Concurrent turns never share executor state |

## Tradeoff I can defend

The action must match the target, or the request is treated as ambiguous. This rejects some answers a human would accept, for example `target: orders` with `refund_order`, which the rules say belongs to billing. Those customers get a clarifying question instead of a guess. The upside is that a single model can't route a request to a team that doesn't own that action, and every disagreement shows up in `support.triage.decisions{unrouted_reason=ambiguous_request}`, where a rising rate is easy to spot.
