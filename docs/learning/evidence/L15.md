# L15 - Add bounded timeouts, retries, and graceful failure

> **Authorship:** The assistant (Claude Code) implemented this ticket and drafted this note. Per the owner's choice, interview questions and tips are given in chat rather than recorded here.

## What I built

- **`ResilienceOptions`** (configuration section `Resilience`), every limit in one place:
  - turn deadline 90 s;
  - 10 model calls per turn;
  - 4 tool steps per agent run;
  - 10 s per tool call;
  - SDK retries 2;
  - 30 s per model attempt;
  - 1024 output tokens per call.
- **One retry owner for model calls: the Anthropic SDK.** The probe below shows exactly what it retries.
  - Our code creates its `HttpClient` directly, so the service defaults' standard resilience handler can't add a second layer.
  - `ProviderAttemptHandler` (under the SDK) counts HTTP attempts and captures the `retry-after` hint, which the SDK honours but doesn't expose. It never retries itself.
- **Per-turn limits:**
  - **`TurnBudget`** (an AsyncLocal per turn) plus **`BudgetedChatClient`**, the outermost layer of the model pipeline: each model call is counted, and the 11th is refused before it reaches the provider → `budget_exhausted`.
  - **A turn deadline** on the server's `TimeProvider`, joined with the cancel token → `timeout`. For an approved write it's `failed`/`timeout` with nothing changed.
  - **Each agent's MAF function-invocation loop is bounded** via `agent.GetService<FunctionInvokingChatClient>()`:
    - `MaximumIterationsPerRequest` = 4;
    - a per-tool timeout in its `FunctionInvoker` → `tool_unavailable`;
    - `MaximumConsecutiveErrorsPerRequest` = 0, so a failing tool ends the turn instead of being retried by the model.
- **Classification (`TurnErrors`):** rate limit → `rate_limited` plus `retry_after_seconds`; 5xx/overloaded/connection → `model_unavailable`; timeouts → `timeout`; tool → `tool_unavailable`; budget → `budget_exhausted`; permanent 4xx and anything unexpected → `internal_error`. The detail text is fixed and safe.
- **Span tags on `support.turn`:** `support.turn.model_calls`, `support.turn.model_attempts`, `support.turn.error_code`.
- **Docs:** `docs/observability.md` gains "Failures, retries and budgets": the retry inventory, the worst case, and the error codes.

## Native behaviour check (probe, deleted afterwards)

The real Anthropic SDK 13.7.0, run against a fake HTTP handler with `MaxRetries` = 2:

| Response | Attempts | Spacing | Exception |
| --- | --- | --- | --- |
| 500, 500, then 200 | 3 | about 0.5 s, then 0.8 s | none (success) |
| 500 every time | 3 | | `Anthropic5xxException` |
| 400 | **1** (not retried) | | `AnthropicBadRequestException` |
| 429 with `retry-after: 1` | 3 | **about 1.0 s** (the hint is honoured) | `AnthropicRateLimitException` (no retry-after property) |
| 529 overloaded (MaxRetries 1) | 2 | | `AnthropicOverloadedException` |

- The MAF agent exposes its `FunctionInvokingChatClient` via `GetService`. Its defaults are 40 iterations and 3 consecutive errors, both too loose for us.
- This matches the SDK documentation: it retries connection errors, timeouts, 408, 409, 429 and 5xx. No disagreement.

## Course versus current implementation

| Course | Here | Why |
| --- | --- | --- |
| No timeouts or limits on agent runs | Turn deadline, model-call budget, tool step and time limits | Unbounded loops cost money and hang users |
| Errors bubble up as exceptions | Classified `failed` outcomes with safe text and a trace id | Clients can act on a code; users see no internals |
| Default SDK/HTTP behaviour, implicit | One retry owner, documented and tested | Stacked retries multiply attempts and latency |

## Tradeoff I can defend

**Fail the turn rather than let the model retry a failing tool.** Feeding the error back lets a model sometimes recover, but it also invites retry loops that spend budget and time on a tool that's down. With `MaximumConsecutiveErrorsPerRequest` = 0, a tool fault is one clear `tool_unavailable`, and the client decides whether to try again. The cost is less "self-healing" on flaky tools; today all tools are local and deterministic, so that cost is small.

## Remaining questions

- **A circuit breaker:** during a provider outage every turn still spends 3 attempts. A breaker would fail fast.
- Per-customer rate limiting, and a token or spend budget (not just a call count), are not built.
- The tool step limit's exact end state (the run returns with an unanswered tool call) is bounded and safe, but not mapped to its own code. The turn budget is the primary loop guard.
