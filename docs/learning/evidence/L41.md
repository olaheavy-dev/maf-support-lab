  - after approval: a second write, and **the approved tool with changed arguments**;
  - the rejection reason;
  - a paraphrase that bypasses the heuristic while the gate holds (**the stretch**); a false positive that's recorded but harmless;
  - the poisoned article flagged on its tool span, with its text absent from telemetry;
  - customer "SYSTEM:" text staying a user message; markup returned as plain JSON (turn result and SSE);
  - bounded, printable tool arguments; an overlong or control-character search rejected without running.
- **The threat model** has a Python section (attack, gate, test). It doesn't claim complete prevention.

## A Python difference worth knowing

The **rejection reason never reaches the model in Python.** MAF Python's `to_function_approval_response()` has no reason field (L37), so the reason is audit-only. In .NET it reaches the model with the native rejection. The test proves the text appears in no model input, and that nothing changes.

## Course versus current implementation

| Course | Here | Why |
| --- | --- | --- |
| `security.py` phrase matching that **blocks** messages | A phrase heuristic that only **records** (names, never text) | Blocking refuses real customers (false positives) and is bypassed by any paraphrase |
| Safety depends on the model refusing | Gates in code: ownership, exact-argument approval, eligibility, argument validation | An obedient model is the realistic worst case; the tests assume it |

## Tradeoff I can defend

**Detection that never blocks.** A blocking filter feels safer, but here it would refuse "Please ignore my previous message, where is ORD-1002?" while letting "Kindly set aside the guidance…" through. The value of the heuristic is visibility: it shows *which* attacks arrive and from where (message, reason, or tool result) without storing customer text. The protection comes from controls that hold whatever the text says.
