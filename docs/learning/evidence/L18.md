# L18 - Implement Python read-only agents, tools, and triage

> **Authorship:** The assistant (Claude Code) implemented this ticket and drafted this note. Per the owner's choice, interview questions and tips are given in chat rather than recorded here.

## What I built

Ported L05/L07/L08's read-only behaviour to Python (MAF Python 1.25.0), using idiomatic Python types:
- **Records:** frozen Pydantic records from the shared fixtures (`domain.py`, `fixtures.py`).
- **Owner-checked services** (`services.py`): another customer's order or invoice is `None`, exactly like a missing one; ids are validated first.
- **Tools** (`tools.py`, MAF `@tool`): ids only, never a customer id or a confirmation. They read the **pinned** principal (`identity.pinned` / `current_principal`), which fails closed when nothing is pinned, and record outcomes in a `contextvars` turn activity.
- **Agents** (`agents.py`): MAF `Agent`s (triage, orders, billing, technical) with the .NET instructions, minus writes. Each specialist has only its own read tools; triage has none.
- **Triage and routing** (`routing.py`, `contract.py`):
  - triage asks for structured output (a Pydantic `TriageDecision`), but its text is **untrusted until it passes the full contract schema** (jsonschema over `contracts/schemas`);
  - then code decides: the action must belong to the target's team, `other` is never routed, and an order action without an id asks for it.
- **Workflow** (`workflow.py`, MAF `WorkflowBuilder` with `Case`/`Default`):
  - triage → switch → `ask-for-order-id` / `write-not-available` / one specialist / `unrouted` → `reply`;
  - specialists get the customer's **original message**;
  - progress steps are typed `data` events;
  - a DevUI variant swaps only the two ends.
- **Contract API** (`api.py`, `conversations.py`):
  - `POST/GET /api/v1/conversations`, `POST …/turns`, `GET …/turns/{id}`;
  - every body is validated against the shared schema (unknown fields such as `customer_id` → `400` with JSON pointers);
  - foreign = missing → `404`, the same body apart from the trace id;
  - `client_turn_id` replay, `409 client_turn_id_reused`, `409 turn_in_progress`;
  - a failure is `200`/`failed`/`internal_error` with no internals.
- **Fake model** (`fake_model.py`): built from **MAF's real chat-client layers** (`FunctionInvocationLayer`, `ChatMiddlewareLayer`, `ChatTelemetryLayer`) over a scripted core, so the real MAF tool loop runs in tests. Keyword triage and the tool script are ported from .NET, with the same failure markers.
- **Python DevUI** (`devui.py`): a separate development-only process on loopback (`uv run python -m support_agent.devui`), started by the AppHost as `support-devui-python`. It lists orders, billing, technical and `support-routing` over the same services.
- **Tests:** 60 unit/API tests plus 7 opt-in live tests (`uv run pytest -m live`).
- **New dependencies** (exact pins, locked): `agent-framework-devui` 1.0.0b261106 (prerelease, unavoidable) and `jsonschema` 4.26.0.

## SDK conventions vs observable behaviour

| Aspect | .NET | Python | Observable difference? |
| --- | --- | --- | --- |
| Tool definition | `AIFunctionFactory.Create(method)` | `@tool` on a function with `Annotated` parameter descriptions | None |
| Identity in tools | AsyncLocal `PrincipalScope` / `IPrincipalSource` | `contextvars` pin (`identity.pinned`) | None (both fail closed) |
| Structured triage | `ChatResponseFormat.ForJsonSchema` + JsonSchema.Net | `response_format=TriageDecision` + jsonschema over the same file | None |
| Workflow switch | `AddSwitch(...).AddCase(...)` | `add_switch_case_edge_group([Case, Default])` | None |
| Progress events | custom `WorkflowEvent` subclasses | a typed `data` event (Python's event types are a closed list) | None (internal) |
| DevUI | in-process at `/devui/` | **its own process** (the UI calls `/v1` at the root; sub-app lifespans don't run) | Only the URL: same entities, same guards |
| Unrouted route JSON | `"target": null` | the same (the contract test caught my first version, which omitted it) | **None, after the fix** |

## Course versus current implementation

| Course (Python) | Here | Why |
| --- | --- | --- |
| `tools.py` returns any customer's record by id | Owner-checked services; the tools read a pinned principal | Knowing an id is not permission |
| `models.py` trusts parsed model output | Full contract-schema validation, then code routing rules | Valid shape ≠ correct or authorized |
| Specialists get the triage summary | They get the original message | A summary can drop or distort details |
| Refund and ticket tools registered | No write tools until the approval gate (L37) | An unapproved write tool is one injection away from acting |

## Tradeoff I can defend

**DevUI as its own process.** Mounting it inside the API would mean one URL, but the DevUI UI expects to own `/` and `/v1`, and its startup and cleanup wouldn't run as a mounted sub-app. A separate loopback process keeps the API surface clean and lets DevUI's own host guard work. It shares the code, not the process. The cost is one more resource in Aspire.
