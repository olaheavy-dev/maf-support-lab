# L20 - Implement Python streaming and cooperative cancellation

> **Authorship:** The assistant (Claude Code) implemented this ticket and drafted this note. Per the owner's choice, interview questions and tips are given in chat rather than recorded here.

## What I built

Ported L12 to Python (MAF Python 1.25.0, FastAPI 0.162.3), on the shared contract 1.1. No contract change.

- **Streaming:** `Accept: text/event-stream` on `POST …/turns` and `POST …/approvals/{id}`.
  - The specialists run `agent.run(stream=True)`. Executors publish progress (`triage`, `routed`, `specialist`, `tool_call`, `awaiting_approval`) and reply text as native workflow `data` events.
  - `run_turn` reads `workflow.run(stream=True)` and sends them to the turn's `TurnControl`. A resumed approval streams the same way and adds `executing_operation`.
  - `streaming.py` writes `turn.started`, the live events, and exactly one `turn.final` carrying the stored turn, using FastAPI's `EventSourceResponse`.
  - If the reply the server settles on differs from what streamed (an approval request, a declined write, a failure or a cancellation), it sends `reply.reset` and then the real text. Deltas are split at 2000 characters; Python strings are code points, so a split never breaks a character.
  - Errors before the start stay JSON problems. A duplicate submission gets the stored turn's text and final, with no live events.
- **Buffering, chosen explicitly:** nothing is buffered in the app. Responses send `Cache-Control: no-cache` and `X-Accel-Buffering: no`, and a `: keepalive` comment every 15 seconds. (FastAPI's own keepalive constant says `ping`; the contract says `keepalive`.)
- **Cooperative cancellation** (`turn_control.py`):
  - `POST …/turns/{id}/cancel` returns `202`, `409 turn_already_finished` or `404`. It sets the turn's cancel flag and calls `task.cancel()`, so an in-flight model call stops at its next await.
  - **The pre-commit boundary** is in `OperationService.execute_approved`, now async: once cancellation was requested, no write starts.
  - `TurnCancelled` subclasses `asyncio.CancelledError`, because MAF's tool layer turns ordinary exceptions into an error result and the run would continue.
  - **Before the commit:** the turn is `cancelled` and the operation `failed` with code `cancelled`; nothing changed.
  - **After the commit:** the committed result stands, and the turn completes from the record.
- **Disconnects aren't cancellations.** The stream detaches from the turn, and the turn runs on and is stored.
- **Shutdown** (`RunningTurns`): running turns are cancelled cooperatively and stored before the database and clients close.
- **The fake model** streams word by word, with a message id per response like a real provider. Test hooks: `between_updates` and `OperationService.before_commit`.

## Native SDK check (MAF Python 1.25.0)

A throwaway probe, deleted afterwards, showed:
1. **Workflow `data` events arrive live**, not batched at the superstep's end (0.0, 0.3 and 0.6 s apart).
2. **`agent.run(stream=True)` sends the model's text before the `function_approval_request`.** The final response still carries the request. This is the same reason .NET needed `reply.reset`.
3. **`task.cancel()` surfaces as `CancelledError`** through `workflow.run(stream=True)`.
4. `ResponseStream` is an async context manager with `close()`, so streams are closed deterministically (`async with`).

## A real bug found live, and how it's now caught in fake mode

- **Found:** in the L39 impersonation check, Claude once answered "cancel ORD-1003" with **`get_order_status` and `cancel_order` in one response**. The decline then got Anthropic `400: unexpected tool_use_id found in tool_result blocks`.
- **Cause** (read in MAF's `_tools.py`): in a mixed batch, MAF pauses the approval-required call, **keeps the other calls in the session**, runs them when the batch is answered, and sends their results too. L37's `answer()` re-sent only the paused call, so the read's result had no call before it. This was latent since L37; streaming didn't cause it, it just happened to be the run where Claude made parallel calls.
- **Fix:**
  - `approval_gate.batch_of()` finds every call of the paused turn, and `answer()` and `decline()` re-send the whole batch;
  - the batch is stored with the native request (durable, so a restart still works), and the old stored shape is still read.
- **So it can't recur:** `tests/test_tool_batches.py` (4 tests) makes the fake model ask for a read and a write together, with the fake enforcing Anthropic's pairing rule. Reverting the fix makes 3 of them fail.

## Codex review fix

- **Finding (P2):** a turn cancelled right after `detach()`, before its task first ran (for example by shutdown), never reached its handler. `task.cancel()` on an unstarted task skips the coroutine body. So no turn was stored, waiters hung, and an approved operation stayed `running`.
- **Fix:** `request_cancel()` only interrupts a task that has started. Each turn marks itself started and checks the flag as its first step, inside its own cancellation handler.
- **Tests:** two new tests (a turn, and an approved decision) detach then shut down immediately: the turn is stored `cancelled`, the operation `failed`/`cancelled`, nothing changed. Restoring the old behaviour makes both fail.

## Course versus current implementation

| Course | Here | Why |
| --- | --- | --- |
| A buffering middleware that collects output before sending it | Live token deltas, no app buffering, proxy buffering turned off | "Streaming" that buffers shows nothing until the end |
| No cancellation model | Cooperative cancellation with a pre-commit boundary and factual outcomes | Cancellation must never undo or hide a committed write |
| The connection is the turn | The turn is a detached task; the connection only observes it | A disconnect must not change business state |

## Tradeoff I can defend

**Interrupt with `task.cancel()`, and also check a flag at the pre-commit boundary.** The task cancel stops an in-flight model call quickly. The flag is the guaranteed boundary: it holds even if a library swallows a `CancelledError`. The mutation table shows each one is load-bearing on its own (6 and 1 failing tests). The cost is two mechanisms to understand instead of one.
