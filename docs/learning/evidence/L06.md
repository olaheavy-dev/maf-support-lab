# L06 - Export traces, metrics, and structured logs to Aspire

> **Authorship:** The assistant (Claude Code) implemented this ticket and drafted this note. The interview answers are **assistant-drafted reference answers**.

## What I built

- **One pipeline, explicit subscriptions.**
  - `Support.ServiceDefaults` keeps the only OpenTelemetry provider and OTLP exporter, for traces, metrics, and logs.
  - `SupportTelemetryRegistration` (Common/Infrastructure) subscribes `Support.Api` and adds `service.version` and `deployment.environment.name`.
  - `AgentTelemetryRegistration` (Agents/Infrastructure) subscribes `Support.Agents` and `Support.Model`, and adds a View that drops the agent layer's duplicate token usage.
- **Agent layer:** `SupportAgents` wraps every registered agent with MAF's `OpenTelemetryAgent` (source `Support.Agents`), so future specialists get it automatically.
- **Model layer:** `ModelProviderRegistration` registers the raw provider client under a DI key, and exposes `IChatClient` as that client wrapped once with `OpenTelemetryChatClient` (source `Support.Model`). Since the client is already instrumented, MAF's auto-wiring adds no second chat wrapper. Tests swap the keyed client, so scripted models are instrumented too.
- **App signals:**
  - `support.turn` span with conversation, client-turn and turn ids, outcome, and reply kind; on failure, error status, `error.type`, and an exception event;
  - `support.turns` and `support.turn.duration`, recorded by `TurnMetrics`;
  - `support.tool.calls`, recorded by `ToolMetrics`;
  - two `LoggerMessage` logs, "turn completed" and "turn failed", plus a tool-outcome log.

  There is no message text or customer id anywhere.
- **Sensitive data:** `Telemetry:CaptureSensitiveData` defaults to false and is always set explicitly on both AI layers.
- **Fake model:**
  - fixed usage of 100 input and 20 output tokens per call, so metrics have samples;
  - `[fake:model-error]` throws, giving a failure case.
- **DevUI in Aspire:**
  - the AppHost adds a **DevUI** link to the `support-api-dotnet` resource (`WithUrlForEndpoint`, relative `/devui/`);
  - a telemetry test proves a DevUI chat is traced through the same agent, model and tool spans, without `support.turn` or turn metrics.
- **Tests:** 6 telemetry tests through in-memory exporters on the real pipeline, in a non-parallel collection. The test process runs with `OTEL_INSTRUMENTATION_GENAI_CAPTURE_MESSAGE_CONTENT=true`, set by a module initializer.
- **Docs:** [docs/observability.md](../../observability.md) covers how to view the telemetry, the trace shape, signal ownership, metrics and labels, service identity, and sensitive data.

## How the request flows (as telemetry)

1. **HTTP span:** ASP.NET Core starts it. Its trace id becomes the turn's `trace_id` in the response.
2. **`support.turn`:** the handler opens this span under the HTTP span, after the duplicate check. A replay records outcome `replayed`; a 409 conflict gets no turn span and stays visible as an HTTP 409.
3. **`invoke_agent orders`:** `OpenTelemetryAgent` opens it on `Support.Agents`.
4. **Inside the agent run:** function invocation produces two `chat` spans on `Support.Model` (one per model call, each with its own token usage) and one `execute_tool get_order_status` span on `Support.Agents`.
5. **Logs:** the tool and the handler log inside these spans, so every log line carries the same trace id.
6. **Metrics:** the turn and tool counters and the turn histogram record with bounded labels.

## Interview answers (assistant-drafted reference)

1. *Why does seeing a trace not prove metrics are configured?* Traces and metrics are separate pipelines. A tracer provider subscribes to `ActivitySource`s; a meter provider subscribes to `Meter`s, by name, with their own readers, export intervals, and Views. You can see perfect traces while a meter was never added, or while a View drops the instrument. Metrics also arrive later, on the export interval, not when the request ends. This project shows it directly: the CLI export showed traces and logs but no metrics. The proof for metrics came from reading metric points, not spans.
2. *How do you correlate a request while avoiding sensitive data in telemetry?*
   - Correlate with ids, not content. The trace id ties HTTP, the turn, the agent, model calls, tools, and every log line together, and the API returns it to the client.
   - Business ids (conversation, turn) go on spans and logs, where high cardinality is fine, but never on metric labels.
   - Content (prompts, replies, tool arguments, customer ids) stays out by default.
   - Turning capture on is an explicit, documented switch that a stray environment variable can't flip.

## Course versus current implementation

**Course (`dn-tracing`, Chapter 6):** its own `TracerProvider` and exporter, `AddSource("Microsoft.Agents.*")`, and traces only.

**Here:**
- one Aspire service-defaults pipeline for traces, metrics, and logs;
- explicit source names per layer;
- no second provider or exporter.

**The release-tagged MAF sample** instruments both the chat client and the agent with one source name and `EnableSensitiveData = true`. Both are changed here:
- separate sources, so the duplicate token metric can be dropped;
- sensitive capture off by default.

**The MAF docs** warn that agent and chat-client telemetry duplicate information, but don't say how to avoid double-counting tokens. This ticket measured it and fixed it with a View.

## Tradeoff I can defend

Agent-level token usage is dropped from metrics, not model-level. The provider bills per model call, so per-call figures are the truth that cost dashboards should sum. The run total is still on the `invoke_agent` span. The cost is one View that depends on the instrument name `gen_ai.client.token.usage`. If the GenAI conventions rename it, the test fails loudly rather than silently double-counting again.
