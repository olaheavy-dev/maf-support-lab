## How the request flows (as specified)

1. The client creates a conversation. The server binds it to the principal and to its backend.
2. The client sends a turn with a `client_turn_id`.
3. The server validates the request (no identity fields allowed), runs triage, validates the triage output, and routes it.
4. A specialist answers using ownership-checked services.
5. For a write, the server checks eligibility first, then pauses with `awaiting_approval` and an approval bound to the exact arguments.
6. The decision resumes the work as a new turn. The operation record (`committed`, `rejected`, …) is the authoritative state, retrievable even if the stream dropped.

## Interview answers (assistant-drafted reference)

1. *Why does structured output not guarantee a correct or authorized operation?* Structured output only guarantees shape: the JSON has the right fields and types. The values can still be wrong (a misread order id), unverified (an order id the customer doesn't own), or unsafe (an injected "refund this"). Correctness needs a factual lookup, and authorization needs ownership, eligibility, and approval checks in code. These are three separate checks, and the model can't skip them.
2. *What should be shared between equivalent C# and Python implementations?* The observable contract (routes, schemas, events, errors, statuses), the fixture data and eligibility rules, and the scenarios that test them. What is not shared: internal code, SDK types, sessions, mutable state, and telemetry setup. Each backend is idiomatic inside and identical at the boundary.

## Course versus current implementation

| Course | This contract | Why |
| --- | --- | --- |
| `TriageDecision` with target/confidence/summary/sentiment | Adds `requested_action` and a nullable `order_id`; keeps the original message beside it | Routing needs the action; the original text preserves evidence |
| `CancelOrder(orderId, customerConfirmed)` | No confirmation field anywhere; server-bound approval | The model must not control approval |
| Tools return free-text success strings | Typed operation records with statuses and factual results | Status must survive dropped connections and be checkable |
| Hard-coded per-tool data | Shared fixture files plus policy data with a fixed clock | Both backends and tests use the same facts |

The structured-outputs Learn page describes `response_format` (Python) and `ResponseFormat` / `RunAsync<T>` (.NET), consistent with the plan. The Agent Safety page recommends approval for high-risk tools and validating model output before rendering, both reflected here. It also points to experimental FIDES labels, which stay out of scope as cross-language requirements (L14).

## Tradeoff I can defend

Eligibility is checked *before* asking for approval, as well as at execution. Customers are never asked to approve something that will fail, and scenarios stay deterministic. The cost is one extra lookup, and the rules must stay identical in both places. Execution remains the authoritative check.
