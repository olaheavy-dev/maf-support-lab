# L25 - Run fault, concurrency, and bounded load exercises

> **Authorship:** The assistant (Claude Code) implemented this ticket and drafted this note. Per the owner's choice, interview questions and tips are given in chat rather than recorded here.

## What I built

- **`load` command** (`evaluations/dotnet/Support.Evaluations/Load/`). It launches one backend in fake mode, one process per customer, reusing `ProcessSession`. It runs 8 scenarios: isolation at concurrency 1, 4 and 16 (96 turns per level); duplicate submission; turn in progress; duplicate approval; decision race; and faults under load. Writes run on a fresh store per scenario.
  - **`LoadClient`:** timed black-box HTTP.
  - **`LoadScenarios`:** the scenarios and their correctness checks.
  - **`ScenarioResult`:** p50, p95, p99, max and mean latency, throughput, and HTTP status and outcome counts.
  - **`LoadCommand`:** options, the target and workload description, and a schema-checked document.
- **`evaluations/schemas/evaluation-load.schema.json` (1.0):** target (OS, CPUs, launch), workload, cost (`available: false` with a reason, never zero), runner, scenarios and summary.
- **CI:** the `cross-backend` job runs `load` on both backends (timeout 15 → 20 min). The checks gate; the timings are recorded only.
- **`compare` now skips non-run documents** (load, quality). Without this, the CI comparison step would have failed on `load-*.json`.
- **The improvement:** `SupportDatabase` now uses pooled connections (`Pooling = true`). The reason is in the code comment and ADR 0003.
- **Docs:** `docs/evaluations/load.md` (scenarios, results over 3 runs, bottlenecks, the improvement, limitations, reproduce). It is linked from the documentation index, the evaluations index, `evaluations/README.md` and the reports lanes table.

## Verification (assistant-run, 2026-11-12)

- **Load, final:** 3 runs per backend on a quiet machine (macOS, 18 CPUs); **every check passed in every run** on both backends. The ranges are in [load.md](../../evaluations/load.md#results-assistant-run-2026-11-12).
  - **No leakage:** 96 turns per level across both customers, and no reply named another order.
  - **One turn per `client_turn_id`:** 16 copies gave one turn.
  - **Busy conversations refuse:** 8/8 got `409 turn_in_progress`, and the slow turn was cancelled.
  - **One write per approval:** 16 approvals of one ticket gave one resumed turn and committed `TKT-0001`, and the probe ticket was `TKT-0002`: the write ran exactly once.
  - **One winner per race:** 8 approve versus 8 reject gave exactly one winner, with the other 8 getting `409 approval_already_decided`, and the probe ticket matched the winner (a single write, or none).
  - **Failures contained:** failed turns stayed in their own conversations, and those conversations recovered.
- **Pooling experiment** (.NET, concurrency 16, 3 runs per variant):

  | Metric | `Pooling = false` | `Pooling = true` |
  | --- | --- | --- |
  | decision-race p95 | 156–179 ms | 20–22 ms |
  | duplicate-approval p95 | 37.5–186 ms (two runs over 150) | 25–27 ms |
  | isolation-c16 throughput | 608–686 req/s | 1,088–1,486 req/s |

  After the change: the full .NET suite passed 3 times with 0 failures; launch-mode evaluations passed 31/31 per backend, including restart and resume; and the 29 probes agree.
- **Codex review (P2, fixed):** status checks couldn't count writes, since `committed` or a cancelled order looks the same after one write or several. Both write scenarios now use tickets plus a probe ticket, whose number counts the writes. A fake that repeats the write behind the same replayed turn now fails, and the 'write count not checked' mutation is caught.
- **Tests:** `LoadTests`, 9. A misbehaving fake API proves each check can fail:
  - a reply naming another order;
  - a turn returned for another conversation;
  - copies creating separate turns;
  - both decisions winning.

  Also covered: percentile, throughput and count arithmetic; a failed check fails its scenario, and the document matches its schema; and `compare` and `report` leave load documents out. The evaluation suite has **87 passed**.
- **Mutation checks (5/5 caught, each reverted):** leak check blind, conversation check blind, duplicate-turn check blind, two winners allowed, write count not checked.
- **My mistakes, caught and corrected:**
  - The first fault check expected `model_unavailable`. The `support-failure` dataset defines `internal_error` for that marker, so the check now follows the dataset.
  - The first workload gave concurrency 1 only 5 requests. It is now a fixed 96 turns per level.
  - The first final runs overlapped my builds, so I re-ran them on a quiet machine.
  - The before-pooling duplicate-approval range first read "156–186 ms". The third run was 37.5 ms, and the docs now say so.
- **Live:** none (see the tradeoff below).

## Course versus current implementation

| Course | Here | Why |
| --- | --- | --- |
| A single happy-path run of the orchestrator | Concurrency and fault scenarios with correctness checks, on both backends, in CI | Guarantees that hold for one request can break under concurrency, so they are tested under concurrency |

## Tradeoff I can defend

**No live load.** A live run would measure the provider's latency and rate limits, costs money per turn, and isn't reproducible. The questions here are whether *our* code keeps its guarantees under concurrency and where *our* overhead is. Fake mode answers both, deterministically and for free. The per-turn model-call cap already bounds what a single live turn can cost.

## Remaining questions

- Python's failure path is about 2.5× slower under load than success. A profile of one failed turn is the next step. Candidates are exception classification and the logging or telemetry of the failure.
- Python's throughput plateau is a single event loop doing synchronous SQLite. Moving storage calls off the loop, or adding Uvicorn workers (which needs a store shared across processes), are the options. Neither is measured yet.
