  - `docs/evaluations/README.md` (adds quality and reports) and `docs/testing.md` (the link check).
- **`scripts/check_docs_links.py`** (standard library only). It reads the Markdown files Git tracks, so ignored or generated output is never checked.
  - **What it checks:** inline links and images, reference definitions, and HTML `href`/`src` outside code blocks and inline code. A target file or folder must exist inside the repository, and a `#anchor` must match a heading (GitHub's slug rules, with `-1`, `-2` for duplicates) or an explicit HTML anchor.
  - **Reachability:** every page under `docs/` must be reachable from `docs/README.md` by following relative links.
  - **Offline:** external links are not fetched, so CI stays deterministic.
- **CI:** a *Check documentation links* step in `planning-and-contracts`, which is in the required `repository-checks` aggregate.

## Course versus current implementation

| Course | Here | Why |
| --- | --- | --- |
| One project's README per chapter | One index, a reading order, and pages that link to the code-level READMEs instead of copying them | A single source per fact, and nothing to keep in sync |
| — | A link and reachability check in required CI | Plain Markdown has no build to catch a broken link or an orphan page |

## Tradeoff I can defend

**Checking links offline only.** Fetching external links would catch dead URLs, but it makes CI depend on other sites' uptime and rate limits, so a required check could fail for reasons unrelated to the change. Relative links, anchors and reachability are what this repository controls, so those are the required checks. External links are pinned to commits where possible, which is in `sources.json`.
