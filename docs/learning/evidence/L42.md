# L42 - Bound Python retries, timeouts, and execution budgets

> **Authorship:** The assistant (Claude Code) implemented this ticket and drafted this note. Per the owner's choice, interview questions and tips are given in chat rather than recorded here.

## What I built

Ported L15 to Python (MAF Python 1.25.0, Anthropic SDK 1.17.0).

- **`ResilienceSettings` (`RESILIENCE__*`)**, with the same defaults as .NET:
  - a 90 s turn deadline;
  - 10 model calls per turn;
  - 4 tool rounds per agent run;
  - 10 s per tool call;
  - 2 SDK retries;
  - 30 s per model attempt;
  - 1024 output tokens.

  Out-of-range values refuse to start.
- **One retry owner, the Anthropic SDK.**
  - `model_provider.py` now builds the `AsyncAnthropic` client itself with `max_retries` and the per-attempt timeout, and hands it to MAF.
  - The app owns that client and closes it at shutdown, because MAF leaves a client it was given open.
  - An SDK middleware (`count_attempts`) runs once per HTTP attempt inside the SDK's retry loop and counts it for the turn.
- **`support_agent/resilience.py`:**
  - **`ModelCallBudget`:** a chat middleware on every agent. The budget is a `ContextVar`, set per turn and per resumed decision. The call over budget is refused before it reaches the provider → `budget_exhausted`.
  - **`ToolLimits`:** a function middleware with a time limit per tool call. Any tool fault becomes MAF's fail-closed `MiddlewareFailure` → `tool_unavailable`. An ordinary exception would otherwise go back to the model as an error result, inviting a retry loop.
    - Argument validation errors still go back to the model to correct, bounded by the loop and the budget.
    - Write tools report business refusals as results, never as exceptions.
  - **`classify`:** walks the error chain, including MAF's `ChatClientException`, which keeps the provider error in its `args`. Each fault maps to the contract's codes, with fixed, safe text. `retry_after_seconds` is read from the SDK's `RateLimitError` response headers.
- **The tool loop** is capped at 4 rounds through the client's `function_invocation_configuration` (MAF's default is 40). After that, MAF asks for one final answer without tools.
- **The turn deadline:** `asyncio.timeout` around every turn and every resumed decision.
  - **Before the commit:** the operation fails with code `timeout`, and nothing changes.
  - **After the commit:** the committed result stands, and the turn reports it.
  - Retrying the decision replays the stored turn.
- **The `support.turn` span** gains `support.turn.model_calls`, `support.turn.model_attempts` and `support.turn.error_code`. `TurnError` now stores `retry_after_seconds`.
- **Docs:** `docs/observability.md` has "Failures, retries and budgets (Python, L42)" (the retry inventory). The README has a section on the limits and the configuration.

## Native behaviour check (probes, deleted afterwards)

- **MAF Python 1.25.0:**
  - an agent-level `ChatMiddleware` runs for every model call, including inside the tool loop, and its exception ends the run;
  - a `MiddlewareFailure` from function middleware escapes the loop with its cause chained;
  - `max_iterations` = 2 gives 2 tool rounds plus one final call without tools;
  - MAF's tool-loop defaults are 40 iterations and 3 consecutive errors, both too loose here.
- **MAF's Anthropic client** never retries. It wraps errors as `ChatClientException` (401/403 → auth, other 4xx → invalid request, so 429 too) and keeps the original in `args[1]`, chained.
- **The real SDK 1.17.0** over a fake HTTP transport:

  | Response | Attempts | Spacing | Code |
  | --- | --- | --- | --- |
  | 500, 500, then 200 | 3 | ~0.5 s, ~0.8 s | completed |
  | 400 | **1** | | `internal_error` |
  | 500 every time | 3 | | `model_unavailable` |
  | 429 with `retry-after: 1` | 3 | **~1.0 s** (the hint is honoured) | `rate_limited`, `retry_after_seconds: 1` |
  | Never answers (0.3 s per attempt, 1 retry) | 2 | | `timeout` |
  | Connection refused | 3 | | `model_unavailable` |
  | 529 overloaded (1 retry) | 2 | | `model_unavailable` |

  This matches the SDK's documented policy (408/409/429/5xx and connection errors; `retry-after-ms` and `retry-after`). No disagreement with the docs.
- **httpx's `MockTransport` ignores timeouts,** which a real transport enforces. The fake API therefore enforces the request's read timeout itself; without that, a "hanging provider" test would wait out the whole delay and report `model_unavailable`.
- **Sync tools run in a worker thread** (`asyncio.to_thread`). A tool timeout stops the turn from waiting, but the thread finishes on its own. That's harmless for our read-only lookups; the write tools are async.

## Course versus current implementation

| Course | Here | Why |
| --- | --- | --- |
| SDK and agent defaults, implicit (MAF's 40 tool iterations, the SDK's 10-minute timeout) | One retry owner and explicit limits, validated at startup | Stacked or unbounded retries multiply attempts, latency and cost |
| Exceptions bubble up | Classified `failed` results with safe text and a trace id | Clients can act on a code; users see no internals |
| A failing tool's error goes back to the model | A tool fault ends the turn (`tool_unavailable`) | The model can't loop on a broken tool |

## Tradeoff I can defend

**The SDK's client is built by us, not by MAF.** Letting MAF create it would be less code, but its retry count and timeout would then be the SDK's defaults: 2 retries, and **10 minutes** per attempt. Our 90 s turn deadline would hide that, but the limits would be implicit and untested. Building it ourselves makes the one retry owner explicit and configurable, and lets a test inject a fake HTTP API under the real SDK. The cost is owning the client's lifetime, since MAF won't close a client it was given; the lifespan does that, and a test checks it.

## Remaining questions

- **No circuit breaker:** during a provider outage every turn still spends 3 attempts.
- **No per-customer rate limiting**, and no token or spend budget (only a call count).
- A timed-out sync lookup keeps its worker thread until it returns. If a future tool could block for a long time, it should be async (cancellable) or run with its own bound.
