## Interview answers (assistant-drafted reference)

1. *Why should fake mode start without credentials?* Most work (building, testing, CI, demos of routing and guards) doesn't need a real model. If startup required a key, every contributor and CI run would need a secret and could spend money by accident. Validating credentials only when Live mode is chosen keeps the default safe, free, and reproducible.
2. *Why is a client-supplied customer header not authorization?* Anyone can send any header. Trusting it would let one customer act as another. Identity must come from something the server controls, such as an authenticated session, or here a fixed development principal. Tests swap identity through the server's DI container, which no client can reach.

## Decisions and deviations

- `Directory.Packages.props` lives at the **repository root**, not in `src/dotnet/` as L04 listed, because `apphost/` also needs it. L04 adds locked restore on top.
- **Test runner:** the .NET 10 SDK no longer supports VSTest with xUnit v3's platform, so `global.json` selects the Microsoft Testing Platform and the VSTest-only packages were removed.
- **`ASPIRE010` suppressed:** the dashboard and orchestrator come from NuGet so a clean checkout and CI don't need the Aspire CLI. Aspire's own docs page currently headlines CLI 13.6.0, while NuGet's latest stable is 13.6.4; we pin 13.6.4.
- **Locally installed tools are behind:** Aspire CLI is 13.4.5 and the templates are 13.3.5. This doesn't affect the build, but the update commands are in the chat.

## Tradeoff I can defend

Identity is a simple injected service rather than ASP.NET Core authentication handlers. It is easy to understand and test now. The cost is that later real authentication must replace `IPrincipalSource` with one backed by `HttpContext.User`. The rest of the app depends only on the interface, so that swap is local.
