# L11 - Persist pending approvals and prevent duplicate operations

> **Authorship:** The assistant (Claude Code) implemented this ticket and drafted this note. Per the owner's choice, interview questions and tips are given in chat rather than recorded here.

## What I built

- **A local durable store.**
  - `Common/Infrastructure/Persistence/SupportDatabase` is one SQLite file (Microsoft.Data.Sqlite **10.0.15**) at `Storage:Path`, by default `.data/dotnet/support.db`, which Git ignores.
  - It creates the schema and offers small query helpers, a stored id counter, and `IUnitOfWork.AtomicallyAsync`: one `BEGIN IMMEDIATE` transaction that every write inside it joins.
  - The decision record is `docs/decisions/0003-state-and-idempotency.md`.
- **Everything a conversation needs now survives a restart:**
  - `SqliteConversationStore`: owner, verified context, and finished turns with the key they were claimed with, so a repeat replays after a restart. Restore goes only through `FindOwned`.
  - `SqliteOperationStore`: binding, exact arguments, expiry, status, decision, result and failure. It reads fresh every time; every change is a **guarded update** (`… WHERE status = @expected`).
  - `PendingNativeApprovals`: the paused `ToolApprovalRequestContent`, in M.E.AI's own JSON form. It's kept until the resumed run finishes.
  - `ConversationSessions`: each specialist session is saved after every run with `SerializeSessionAsync` and restored with `DeserializeSessionAsync`.
  - **Business state:** changed orders (fixtures never change), refund payments, tickets, and the RFD, PAY and TKT counters.
- **Stable identities:** agents have fixed ids (`orders`, `billing`, `technical`, `triage`); the workflow is `support-routing`.
- **One write, at most once:**
  - `OperationService.ExecuteApprovedAsync` runs the module's write *and* `committed` in one transaction. If the guarded commit finds the operation already finished, the whole write rolls back and the stored result is returned.
  - **Turns:** the first stored turn for a key wins.
  - **A decision retried after a crash:**
    - already finished → a factual turn from the record (no model call, no write);
    - still `running` → nothing was applied, so the stored native request is resumed.
- **Tests:** each test host gets its own temporary database, deleted on dispose. `TestDatabase` lets a test "restart" by starting a new host on the same file.

## How a restart between request and approval works

1. "Please cancel order ORD-1003." The gate stores the operation (`awaiting_approval`) and the native request, the session is saved, and the turn is stored.
2. **The process stops.**
3. The new process gets `POST …/approvals/appr_…`:
   - the conversation loads (only for its owner), and so does the operation, with the same 404, 409 and 410 checks as before;
   - the decision is recorded with a guarded update;
   - the session and the native request are loaded, and `CreateResponse(true)` resumes the exact paused tool call;
   - the cancel and `committed` are written in one transaction;
   - the decision turn is stored, so repeating it replays that turn.

  - **For each of cancel, refund and ticket:**
    - restart between request and approval: the pending approval is listed after the restart, approval commits once, and the state changes once;
    - after another restart, repeating the decision replays the same turn and writes nothing.
  - **After a restart, nothing executes for:** wrong owner (`404`), mismatch (`409 approval_mismatch`), rejection (then `409 approval_already_decided` for a late approve), or an approval that expired while the service was down (`410`, status `expired`).
  - **Five concurrent identical approvals:** all `200`, one turn id, one ticket.
  - **For each write type: the write commits, then the host hangs before replying (a "crash").** A new host on the same file gets the retried decision → `200`, "Done." from the stored record, `committed`, one mutation. When the stuck host finally finishes, it gets the *stored* turn back (first stored turn wins), still with one mutation.
  - **The decision was stored but the run never wrote (a crash before the write):** the retry resumes and commits once, and a repeat replays.
  - **A stale run of a committed operation:** its ticket insert rolls back with the guarded commit, and the stored result is reported.
  - **A conversation's verified context and specialist history survive a restart:** the follow-up "When was it shipped?" answers about ORD-1002, the model sees the earlier message from the stored session, and the first turn replays without a model call.

## Course versus current implementation

| Course | Here | Why |
| --- | --- | --- |
| `RefundWorkflowRunner` keeps the approval in the running process | Operation, native request and session are stored; the decision may come after a restart | An approval wait can outlive a process |
| A refund is "processed" with no record or key | Operation id = durable key; write and `committed` in one transaction; guarded status updates | Retries, duplicates and crashes must not refund twice |
| No restore rules | Restore only through the owning customer and conversation | Durable state is still customer data |

## Tradeoff I can defend

**Sessions plus an operation record, not workflow checkpoints.** Our workflow never pauses mid-run, because an approval ends the turn. So a checkpoint would store a second copy of state with nothing to resume. What must survive is the session, the paused native request and the operation, and those are what's stored. The cost: if a later ticket makes a workflow wait *inside* a run, we'll add checkpoints then.

**Atomic locally ≠ exactly-once externally.** Our write is local, so it can share a transaction with its record. A real payment provider can't. It would need the operation id as an idempotency key, or intent → call → outcome with reconciliation. That's documented in 0003, not built.

## Remaining questions

- Expiry is still lazy (applied when touched), and there are no retention or cleanup rules for stored sessions, turns and operations.
- One process per database file. The in-process "one turn at a time" lock isn't shared across processes. The data stays correct (guards and transactions), but two processes could each run a turn of one conversation.
- In the "stuck host" case, the late host's in-memory context briefly includes its own reply; only the stored turn and context count after a restart.
