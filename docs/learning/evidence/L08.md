# L08 - Complete read-only .NET billing and technical specialists

> **Authorship:** The assistant (Claude Code) implemented this ticket and drafted this note. Per the owner's choice, interview questions and tips are given in chat rather than recorded here.

## What I built

- **`Billing` module** (L43 layout):
  - `GetInvoice` (by `INV-` or `ORD-` id) and `GetPaymentHistory` query handlers, owner-checked against `IPrincipalSource`. Another customer's invoice is reported exactly like a missing one.
  - A fixture repository over `invoices.json` and `payments.json`.
  - `BillingTools` with `get_invoice` and `get_payment_history`. They take ids only, never a customer id.
  - The billing agent, whose instructions require citing ids and forbid claiming refunds or changes.
- **`Technical` module:**
  - a keyword search over `knowledge-base.json`. Only article **keywords** count, so a word that appears in a title doesn't match ("smart fridge" ≠ "Smart Speaker"). It returns at most 3 results, best first.
  - `KnowledgeSearchTool` (`search_knowledge_base`) and the technical agent. **There's no ticket tool.**
- **Shared changes:**
  - `TurnActivity` now records a generic `ToolOutcome` (Found, NotFound, InvalidInput, NoMatch).
  - `Money` moved to `Common/Domain`.
  - The agent names and specialist list live in `SupportAgents`. DevUI lists all three specialists.
- **Workflow:**
  - One generic `SpecialistExecutor` replaces the orders-only executor and the L07 placeholders. It runs the routed agent on the **original message**.
  - A new deterministic `write-not-available` executor handles routed cancel, refund and ticket requests until L10. It returns `escalation_offer` with "Nothing has been changed", and costs no model call.
- **The reply kind comes from tool facts:** Found → `answer`; NotFound → `not_found`; NoMatch → `escalation_offer` (the unresolved issue); no lookup → `clarification`.
- **Fake model:**
  - It picks a tool from the agent's *actual* tool list and answers from the result.
  - Triage knows more technical words.
  - The old messages-only script signature still works, so existing tests are unchanged.

- **DevUI workflow** (added at the owner's request during review):
  - The owner noticed DevUI only listed individual agents. The workflow already ran on every API turn, but DevUI couldn't reach it.
  - `support-routing` is now registered with DevUI (`AddWorkflow`, transient, so it's built per run) next to the three agents.
  - All executors are shared with the API. Every ending now sends its `SupportReply` to one `reply` executor, which is the workflow's single output. The DevUI version swaps only the two ends: a `chat-input` entrance (MAF chat protocol → text → triage) and a reply exit that emits an `AgentResponseUpdateEvent` labelled `[route: … | reply: …]`.

## How the request flows

1. Triage validates the model's decision and applies the routing rules, as in L07.
2. The switch runs, first match wins:
   - write requests → `write-not-available`;
   - orders with no id → `ask-for-order-id`;
   - orders, billing or technical → that domain's `SpecialistExecutor`;
   - default → `unrouted`.
3. **Inside a specialist:**
   - `TurnActivity.Begin()` starts the turn record;
   - the agent runs on the original text and calls only its own read tools;
   - each tool sends a query (ownership is decided there) and records its `ToolOutcome`.
4. The executor turns the recorded facts into the reply kind and yields one `SupportReply`.

## Course versus current implementation

| Course (Chapter 7) | Here | Why |
| --- | --- | --- |
| `ProcessRefund` and `CreateSupportTicket` registered on the agents | No mutating tool at all; write requests answered deterministically | Writes need approval (L10); an unapproved write tool is one prompt injection away from acting |
| Invoices hard-coded and readable for any order id | Owner-checked query handlers over shared fixtures | Cross-customer reads must be impossible, whatever the model asks |
| Specialist runs on triage's `Summary` | Specialist runs on the customer's original message | A model-written summary can drop or distort details |
| `FirstOrDefault` substring match across fixed keys | Keyword scoring over article keywords only, top 3 | Avoids loose matches ("smart" fridge → speaker) |
| "No articles… consider creating a support ticket" | `NoMatch` → `escalation_offer`, nothing created | Honest about what is and isn't possible in this build |

## Tradeoff I can defend

**Specialists instead of one agent with every tool.**
- *Cost:* one extra model call per turn (triage), plus the prompt overhead of each agent.
- *Benefits:*
  - each agent sees only the tools its domain needs, so a billing conversation can't reach order lookups, and vice versa;
  - each prompt stays short and focused;
  - every routing decision is visible and testable.

  The measurable safety property is that "no agent has a write tool" and "billing has exactly two reads" are now checked by tests.
