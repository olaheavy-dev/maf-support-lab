# L16 - Build the shared deterministic behavior evaluation runner

> **Authorship:** The assistant (Claude Code) implemented this ticket and drafted this note. Per the owner's choice, interview questions and tips are given in chat rather than recorded here.

## What I built

- **Launch mode for the runner** (`--launch`): it starts each backend itself, in fake mode, with one process per customer (a backend serves one development customer per process) on one SQLite file.
  - Read-only cases share a store.
  - **Every write case gets a fresh store and fresh processes.**
  - A `restart` step kills the processes and starts them again on the same file.
  - Process trees are killed whole (`dotnet run` and `uv run` start children).
  - Endpoint mode (`--principal`) stays for backends started elsewhere: there, writes need `--allow-writes`, and restarts are skipped.
- **Schema 1.1** (additive; 1.0 documents stay valid):
  - `restart`;
  - `get_operation`, which reads the operation record, the authoritative state, checked with an `operation_result` subset;
  - `cancel_after_start` on a send: the runner reads the stream as it arrives and cancels as soon as `turn.started` names the turn.

  Restart cases must reset their store.
- **A fake-only `[fake:slow-model]` marker in both backends.** The specialist's model call waits 8 s, cancellably, so a running turn can be cancelled from outside, with the same marker and delay in each backend.
- **31 cases** (L29's 27, plus 4 new):
  - `resume-after-restart`: an approval survives a restart and then commits once;
  - `refund-twice`: the second refund is not eligible;
  - `ticket-rejected`, with its record checked;
  - `cancel-a-running-turn`.

  Every approved write now ends with `get_operation`, checking the committed record (order `cancelled`; the refund is recorded against `ORD-1001`).
- **`compare`:** writes `docs/evaluations/baseline.md` from the run documents. It shows each run's identity, each case on both backends side by side, agreement, and latency (median and p90 over passed cases).
- **Runner fixes from my own mutation runs:**
  - a step that builds on a failed step now makes the case *failed*, not *error*;
  - `mentions` records the words found, not the missing ones;
  - case latency is API time only (process startup and restarts excluded);
  - a case whose customer has no process is skipped with the reason.
- **Codex review (PR #103), one valid P2:** streams are read as they arrive (`ResponseHeadersRead`), so `HttpClient.Timeout` covered only the headers, and a backend that stalled mid-stream would have hung the run. Every step now has its own deadline (a linked token over the whole exchange, stream included, default 3 min), and a stall becomes a recorded error. New test: a body that sends `turn.started` and then nothing ends as an error in under a second at 300 ms; without the deadline the test hangs past 90 s.
- **CI:** `cross-backend` runs every dataset and split on both backends in launch mode, writes the comparison, and uploads both. L29's `run_against_backends.py` is replaced.

## The baseline (fake mode, 2026-11-11)

[docs/evaluations/baseline.md](../../evaluations/baseline.md):
- **Results:** 31 of 31 cases pass on **both** backends, and they agree on all 31 (0 failed, 0 error, 0 skipped).
- **Latency, API time over passed cases:** .NET median 7 ms, p90 165 ms; Python median 9 ms, p90 35 ms.
- **Usage:** unknown on every case, recorded as unavailable rather than zero.
- **The evidence is real, not just a status:**
  - The cancel case was cancelled **6 ms** after it started, long before the 8 s model call, and ended `cancelled`.
  - The restart took about 2.2 s (.NET) and 2.9 s (Python) as a real process restart. The approval made before it committed afterwards, and the operation record shows `ORD-1003` as `cancelled`.

## Acceptance: deliberate regressions fail the runner

Each was applied to a backend, run through the same datasets, and reverted.

| Regression | Backend | What the runner reported |
| --- | --- | --- |
| **Wrong route:** billing requests routed to orders | Python | `invoice`, `payment-history` and `refund-approved` failed on `route_target` and `tools` (`get_order_status` instead of `get_invoice`) |
| **Missing ownership guard:** order lookup ignores the owner (the stretch) | .NET | `other-customer-order` and `injection-cross-customer-read` failed: `reply_kind` `answer` instead of `not_found` |
| **Duplicate write:** the "already refunded" rule removed | Python | `refund-twice` failed: the second refund was offered for approval (`awaiting_approval`, not `not_eligible`), which would pay twice |
| A repeated `client_turn_id` no longer replayed by the conversation | .NET | **Not caught, correctly.** The store's "first stored turn wins" (`ON CONFLICT DO NOTHING`) still returns the original turn, so the client-visible guarantee holds. Removing one of two layers is invisible from outside; the duplicate-write case above is the one that matters. |

## Course versus current implementation

| Course | Here | Why |
| --- | --- | --- |
| Manual runs and reading traces | One runner, one dataset, both backends, every write on a fresh store | Repeatable, comparable, and CI-gated |
| — | State from the operation record, never from the reply | Model wording isn't evidence of what happened |

## Tradeoff I can defend

**The runner owns the processes in launch mode.** Starting fresh processes for every write case costs about 2–3 s each, and the runner has to know how to start each backend. In return, isolation is real (a fresh SQLite file), restart and resume can be tested as a genuine crash, and nothing depends on a reset endpoint, which a production API should never have. Endpoint mode stays for backends someone else runs.

## Remaining questions

- **Latency is fake-model latency:** it shows overhead differences, not model time. L32 adds live runs.
- **A cancel during an approved write's commit** isn't in the datasets. The resumed run commits before any model call, so the slow marker can't hold it there. The pre-commit boundary is covered by each backend's own tests (L12/L20).
