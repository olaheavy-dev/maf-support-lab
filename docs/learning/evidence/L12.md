# L12 - Implement streaming, cancellation, and terminal events

> **Authorship:** The assistant (Claude Code) implemented this ticket and drafted this note. Per the owner's choice, interview questions and tips are given in chat rather than recorded here.

## What I built

- **Turns run detached from the HTTP request.**
  - Each turn has its own cancellation (`TurnReservation.CancellationToken`), which only a cancel request triggers.
  - A dropped connection, plain or streamed, neither stops nor undoes the turn. It finishes and is stored.
  - The request just waits for the result.
- **All four outcomes, as the contract says:**
  - `completed`;
  - `awaiting_approval`;
  - `failed`: 200 with `error.code` (`model_unavailable`, `timeout` or `internal_error`) and fixed, user-safe text. It's stored, so a repeat returns it.
  - `cancelled`.
- **Status lookup:** `GET …/turns/{id}` reports `state: running` while a turn runs.
- **Cancellation:** `POST …/turns/{id}/cancel` returns 202 (`cancel-turn-response`). A finished turn gets `409 turn_already_finished`; another customer's or an unknown turn gets 404.
- **Cancellation boundaries:**
  - before the run;
  - every model call (the token);
  - before a resumed approval;
  - **the pre-commit boundary:** `OperationService` checks just before the write's transaction, and the unit of work also refuses to start one once cancelled.
  - **Before the commit:** the turn is `cancelled`, nothing changes, and an approved operation becomes `failed` with code `cancelled`.
  - **After the commit:** the committed result stands, and the turn reports it as completed.
- **Streaming (SSE):** `Accept: text/event-stream` on the turn and approval routes.
  - Executors raise `SupportProgressEvent` and `SupportReplyDeltaEvent` with `IWorkflowContext.AddEventAsync`.
  - The router reads MAF's native stream (`InProcessExecution.RunStreamingAsync` + `WatchStreamAsync`). Specialists run with `AIAgent.RunStreamingAsync`, so **the model's tokens go out live**.
  - `TurnStream` writes the events with ASP.NET Core's `TypedResults.ServerSentEvents`: `turn.started`, `turn.progress`, `reply.delta`, `reply.reset`, and one `turn.final` (the stored turn).
  - It sends `reply.reset` (then the final text) whenever the reply the server settles on differs from what was streamed. Deltas are split at 2000 characters.
- **Contract 1.1** (owner's choice: live model tokens, and a `cancelled` failure code):
  - the new `reply.reset` event;
  - the operation failure code `cancelled`;
  - the text rule now counts only deltas after the last reset;
  - schemas, examples (`stream-reply-reset`, `stream-cancelled`, `operation-failed-cancelled`, and an invalid reset with data), contract tests and the README revision history;
  - the server now reports `contract_version` `1.1`.
- **The fake model streams word by word**, so streaming has several deltas to test.

## Native SDK check (MAF 1.28.0, M.E.AI 10.11, ASP.NET Core 10)

A throwaway probe (deleted afterwards) showed three things:
1. **`RunStreamingAsync` sends the model's text before a `ToolApprovalRequestContent`.** The model said "Sure, I will cancel ORD-1003 now." and then asked for approval. That text can't be withdrawn from a live stream, so the contract needed `reply.reset`. This is the reason for 1.1.
2. **A cancellation observed inside a tool propagates out of the function-calling layer** as `OperationCanceledException`, so a cancel reaches our boundary and stops the run.
3. **Custom executor events come through `WatchStreamAsync` in order, before the workflow's output.**

So everything else in the contract matched the native behaviour. Ownership, exact-argument approval and factual operation state are untouched.

## Course versus current implementation

| Course | Here | Why |
| --- | --- | --- |
| Agents run to completion; the response is returned in one piece | Live token deltas plus progress over SSE, with one terminal event | Faster feedback, still with one authoritative result |
| Python middleware buffers output for filtering | Live tokens, reconciled by `reply.reset` | The owner chose live tokens; the reset keeps the stream honest when the server replaces text |
| No cancellation; a dropped client ends the work | Cooperative cancel with a pre-commit boundary; a disconnect isn't a cancel | Writes must never be half-done, and a lost connection must not lose a committed refund |

## Tradeoff I can defend

**Live tokens with resets, against buffering.** Live tokens show the answer's words while the model is still writing them (here about 0.5 s before the end, on a 4 s turn where triage and tools come first). The cost: the client must handle `reply.reset`, and a customer may briefly see words like "Sure, I will cancel…" that are then replaced by an approval request. Buffering never shows unvetted text, but the first words arrive only at the end. Progress events give early feedback either way.

## Remaining questions

- **Keepalive comments** (`: keepalive` every 15 s) are optional and not sent yet; long tools might need them behind proxies.
- **Per-request identity:** turns now outlive their request. Today the principal is fixed per process. When real per-request authentication arrives (L13), the detached run must carry the caller's principal explicitly. It flows today, but that should be tested then.
- **Shutdown:** a turn still running when the process stops isn't stored (L11 rule). It isn't reported as cancelled.
