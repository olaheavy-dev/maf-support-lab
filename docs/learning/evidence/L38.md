# L38 - Persist Python approvals and atomic operation records

> **Authorship:** The assistant (Claude Code) implemented this ticket and drafted this note. Per the owner's choice, interview questions and tips are given in chat rather than recorded here.

## What I built

Ported L11's local-store design (ADR 0003. The ticket says "ADR 0002" because it predates the renumbering: 0002 became the code-layout decision.) to Python with the standard library's `sqlite3`. No new dependency.

- **One file per backend and run** (`database.py`):
  - the file is `STORAGE__PATH`, by default `.data/python/support.db` (ignored by Git), never the .NET file;
  - each test gets its own file, and DevUI uses its own `devui.db`;
  - `Database.atomically()` is one `BEGIN IMMEDIATE` transaction that nested calls join, via a `ContextVar` connection;
  - every other call uses a short-lived connection, and the lifespan checkpoints the write-ahead log at shutdown.
- **What survives a restart:**
  - conversations and their verified context;
  - finished turns with their claim key (`client_turn_id` or `approval:{id}`);
  - operations (binding, exact arguments, expiry, status, decision, result, failure);
  - the paused native `function_approval_request` (`Content.to_dict()` / `from_dict()`);
  - each specialist's `AgentSession` (`to_dict()` / `from_dict()`, saved after each run);
  - the simulated business state (`changed_orders`, `payments`, `tickets`, `counters`). Fixture files are never changed.
- **Atomic and guarded:**
  - The write and its `committed` record are one transaction. `execute_approved` re-reads the stored status inside it, writes, then commits with a guarded update (`WHERE status = 'running'`). If the guard loses, `Rollback` undoes the business change too.
  - The operation and its paused request are one transaction.
  - A turn and the context it produced are one transaction.
  - The first stored decision wins (guarded); so does the first stored turn (`ON CONFLICT DO NOTHING`, then the stored turn is returned).
- **Recovery:**
  - A retried decision whose write already finished is answered **from the record**: "Done. …", with no model call.
  - One whose decision was stored but whose write never ran **resumes once**.
  - A missing paused request makes an approved operation `failed`, instead of it staying `running`.
  - If storing a turn or decision fails, the reservation is released, so a retry works and the conversation isn't blocked.
  - Approvals of failed turns, and proposals whose turn was never stored, expire.
- **Workflow checkpoints are not used**, as in .NET. The workflow never pauses mid-run; the paused state is the session, the native request and the operation record. Duplicate protection comes from the operation record, not from any checkpoint.

- **`tests/test_durable_state.py`** (26 tests; every case from .NET's `DurableStateTests`, plus Python-specific edges):
  - **Restarts:**
    - for each write, a pending approval survives a restart, is listed, and runs once when approved; a third host replays the same turn with no model call;
    - after a restart: wrong owner `404`, mismatch `409`, rejection changes nothing, a later approval `409 approval_already_decided`;
    - an approval that expired while the service was down → `410`, `expired`, no change;
    - conversation, history and context survive a restart; the first turn replays with no model call;
    - stored turns still match the contract after a restart.
  - **Duplicates and races:**
    - 5 concurrent identical approvals → one turn, one ticket;
    - **two hosts on one file** approving at once → one turn, one ticket;
    - a decision read before another host decided can't overwrite it (`409`).
  - **The stretch, for all three writes:** a write committed just before a crash, with the first host stuck in the model call after the tool result.
    - The restarted host answers "Done." from the record, with 0 model calls.
    - The stuck host then finishes, loses to the stored turn, and returns the same turn id. One mutation.
  - **A crash before the write:** the decision was stored, the write never ran → resumed once; a replay gives the same turn.
  - **Stale runs:**
    - a stale run of a finished operation returns the stored result and writes nothing;
    - a write whose guarded commit loses is **rolled back**, so the tickets table still has 1 row.
  - **Simulated storage failures** (SQLite triggers):
    - an operation is never stored without its paused request;
    - a turn is never stored without its context;
    - an approval whose turn was never stored is not actionable, and the retry asks once more while the orphan expires;
    - a decision that couldn't be stored, at either the turn insert or the operation update, can be retried and doesn't block the conversation;
    - a turn that fails after proposing leaves no actionable approval.
  - **Isolation and resources:** hosts on different files share nothing; Python's default file is its own; shutdown closes the database and leaves no write-ahead log behind.

## Course versus current implementation

| Course | Here | Why |
| --- | --- | --- |
| In-memory state; a restart loses everything | SQLite: operations, paused requests, sessions, turns and business state | An approval must survive the time a customer takes to decide |
| Nothing ties a side effect to its record | One transaction with a guarded commit | No "changed but not recorded", and no double write on a retry |

## Tradeoff I can defend

**Re-read the stored status inside the transaction, *and* guard the commit.** Either one alone stops a duplicate write here, and the mutation table shows the guard alone is enough. Keeping both means a stale run usually writes nothing at all, rather than writing and then rolling back. That matters once a write calls something outside our transaction. The cost is one extra small read per write.

## Remaining questions

- **Exactly-once against a real provider isn't covered:** it needs the provider's idempotency key (the operation id), or intent/outcome records with reconciliation.
- One process per file in production (the per-conversation turn lock is in-process); expiry is lazy; there's no retention policy yet.
